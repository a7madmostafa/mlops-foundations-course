MLflow Tracking

Lesson 2.1 built the smallest honest run recorder by hand. Now professionalize it with the tool MLOps teams actually run — a stable run schema, a searchable store, and a browser UI.

CODE/
Before you start

You need Lesson 2.1 complete: in that lesson's CODE/ folder, uv run flight-delays compare prints the JSONL history in ranked order, and the 77-test suite is green. The shared flight-delays CSV still lives in the data/ folder at the repository root.

What you'll do in this lesson

  • Add MLflow as a dependency and point the project at a local SQLite tracking store so every flight-delay run lands in a real database instead of our hand-written runs.jsonl.
  • Record each run through MLflow: parameters and metrics in its dedicated tables, our data + code fingerprints as tags, and the trained artifact copied under the run.
  • Replace the hand-rolled JSONL reader with MLflow's search_runs query API behind compare.
  • Start mlflow server and browse the same runs with charts, tags, and artifact downloads in the browser.
  • Keep the fingerprint helpers from Lesson 2.1 byte-for-byte unchanged and the quality gates green.

1The hand-rolled tracker reaches its limit

The symptom this lesson fixes: the recorder works, and the day runs multiply, it quietly becomes the bottleneck.

Lesson 2.1 gave run and compare real meaning: every training attempt is a JSON record with parameters, metrics, an artifact copy, and two fingerprints. That is an honest, working tracker — and it is exactly as limited as a hand-rolled tracker must be. Now tune for real: five seeds, two iteration limits, maybe a different test split — that is ten runs. Sit in front of the project on Tuesday and you will feel each edge:

  • The schema is ours alone. runs/runs.jsonl is a format we invented. Every tool that reads it — compare, the next lesson's utilities, your future code — must agree on its key names, ordering, and nesting, forever, by convention.
  • No overview. Comparing ten runs means re-reading a terminal table. There is no page that shows accuracy versus F1 across runs, no chart, no place to group runs by "feature experiment" or "split test".
  • No query language. "Give me the best run where max_iter === 500 and the data fingerprint changed" is answered by reading every line, not by asking the store.
  • Artifacts float free. Model files pile up in a folder, each tied to a run only by a name we remembered to make consistent.

The industry answer is a purpose-built tracking tool, not a hand-rolled file. The most widely used one is MLflow: an open-source project that grew out of Databricks' internal experiment store and became the de-facto standard for this problem. This lesson is the tool turning (the concept we already own) into something a team could share.

2What MLflow Tracking is

Three pieces: a database for run metadata, a folder for artifact files, and two companions readers — a Python API and a web UI.

MLflow is a suite of tools; the piece we need now is Tracking. Tracking's job is exactly Lesson 2.1's job — remember runs and let you compare them — done once, done well, and done the same way across every ML project. Its anatomy:

Three terms do most of the work:

  • Tracking store (backend store) — the database holding run metadata: params, metrics, tags, status, start and end time. We keep it in one local file, mlflow.db, using SQLite — a tiny database engine that stores everything in a single file with no server to run. MLflow's data model is built around databases, and SQLite is the supported choice for solo local work.
  • Artifact store — where files go. The trained model is a file, not a table row, so MLflow copies it under mlruns/<experiment>/<run>/artifacts/ on disk.
  • Experiment and run — the grouping we were missing. An experiment is a named collection of runs (ours is flight-delays); a run is one execution inside it with its own 32-hex run id that MLflow assigns.

The tracking URI is the one configuration that ties it all together: it tells the client where the store lives. Our whole setup is "point everything at mlflow.db, and every run, query, and UI view reads the same history."

3Set it up: one dependency, one store

Add MLflow with uv, then teach the project where its history should live.

MLflow is an ordinary Python package. From the lesson's CODE/ folder, the one-line uv command installs it, resolves its dependency tree, and records the requirement in pyproject.toml and uv.lock:

terminal
uv add mlflow

That adds "mlflow>=3.16.0" to the project dependencies. Next, the configuration. config.py now owns two new constants:

config.py
# --- Experiment tracking --------------------------------------------------- # MLflow keeps run metadata in a local SQLite database. The server command # below reads the same file, so the UI shows exactly what `run` records: # uv run --locked mlflow server --backend-store-uri sqlite:///mlflow.db # Trained artifacts land under mlruns/ next to the database. MLFLOW_TRACKING_URI: str = ( "sqlite:///" + (Path(__file__).resolve().parents[2] / "mlflow.db").as_posix() ) MLFLOW_EXPERIMENT_NAME: str = "flight-delays"

The tracking URI is a URI, not a path: the sqlite:/// prefix tells MLflow "use a SQLite database", and the rest locates the file. It is computed as an absolute path from config.py, so it works no matter which folder you launch from. The experiment name is simply the label under which the runs group themselves. Because mlflow.db and mlruns/ are generated data, both join .gitignore — the history stays on your machine and never reaches the repository.

4Record a run: one training run becomes one MLflow run

The five pieces from Lesson 2.1 map one-to-one onto MLflow's schema — they just land in a database instead of a JSONL line.

Everything Lesson 2.1 taught still holds; the tool changes only where the pieces go:

  • parameters → mlflow.log_params
  • metrics → mlflow.log_metrics
  • the trained artifact → mlflow.log_artifact(…, artifact_path="model")
  • the data and code fingerprints → mlflow.set_tags

Fingerprints are facts we computed (the sha256, the git stamp, the dependency versions), so they ride along as tags — key–value metadata that anything else can later filter on. Here is the recorder from tracking.py in full:

tracking.py
def record_run( params: dict[str, int | float], metrics: dict[str, float], artifact: Path, data: dict[str, str], code: dict[str, object], tracking_uri: str | Path = MLFLOW_TRACKING_URI, experiment_name: str = MLFLOW_EXPERIMENT_NAME, ) -> str: """Log one training run with MLflow and return its run id.""" mlflow.set_tracking_uri(str(tracking_uri)) mlflow.set_experiment(experiment_name) dependencies = cast(dict[str, str], code.get("dependencies", {})) tags = { "data_file": data["file"], "data_sha256": data["sha256"], "git_commit": str(code["git_commit"]), "git_dirty": str(bool(code["git_dirty"])), "python_version": str(code["python_version"]), **{f"dependency.{name}": value for name, value in dependencies.items()}, } with mlflow.start_run() as active_run: mlflow.log_params(params) mlflow.log_metrics(metrics) mlflow.set_tags(tags) mlflow.log_artifact(str(artifact), artifact_path="model") return cast(str, active_run.info.run_id)

Read it as a pipeline of three steps. First, set_tracking_uri + set_experiment point at the store and open its flight-delays experiment. Second, the with mlflow.start_run() context manager opens a run for the duration of the block — MLflow assigns the run its 32-hex id, and any of the log_* calls inside the block attach to it. Third, the three log_* calls and set_tags put each of our five pieces where MLflow keeps it, and log_artifact(…, artifact_path="model") makes the per-run copy under artifacts/model/ — the joblib is no longer overwritten.

Run it, from CODE/:

terminal
uv run flight-delays run INFO flight_delays.cli Pipeline started (max_iter=500, random_state=42) INFO flight_delays.cli Modeling rows: 522,269 INFO flight_delays.cli Training finished INFO flight_delays.cli accuracy: 0.8952 INFO flight_delays.cli f1: 0.7415 INFO flight_delays.cli Saved pipeline to models/model_2025_01.joblib INFO mlflow.store.db.utils Creating initial MLflow database tables... INFO mlflow.tracking.fluent Experiment with name 'flight-delays' does not exist. Creating a new experiment. INFO flight_delays.cli Recorded run 324af2d64480473a848b05418a2b30a1 in experiment flight-delays (tracking uri: sqlite:///CODE/mlflow.db) INFO flight_delays.cli Pipeline finished

Two things to notice. The two mlflow lines appear only on the very first run — they create the database tables and the experiment; the second run's transcript is back to just our logger lines around a single "Recorded run …". And the run id: 324af2d64480473a848b05418a2b30a1 is whatever MLflow generated for that run on that machine — your ids will differ even with identical parameters, because ids must be unique, not reproducible. The metrics reproduce; the ids never do.

5Read runs back: compare is now a search query

The hand-written JSONL reader is gone; compare asks the store directly.

The mirror of recording is reading. Lesson 2.1 wrote its own reader over runs.jsonl; this lesson deletes that reader and asks MLflow instead, because the store knows its own schema. tracking.py now looks like this:

tracking.py
def compare_runs( tracking_uri: str | Path = MLFLOW_TRACKING_URI, experiment_name: str = MLFLOW_EXPERIMENT_NAME, sort_by: str = "f1", ) -> list[dict[str, object]]: """Return recorded runs ordered by one metric, best first.""" mlflow.set_tracking_uri(str(tracking_uri)) if mlflow.get_experiment_by_name(experiment_name) is None: return [] runs = mlflow.search_runs( experiment_names=[experiment_name], order_by=[f"metrics.{sort_by} DESC"], output_format="list", ) rows: list[dict[str, object]] = [] for run in runs: data = run.data rows.append({ "run_id": run.info.run_id, "params": dict(data.params), "metrics": {name: float(value) for name, value in data.metrics.items()}, "tags": dict(data.tags), }) return rows

The two new ideas are small and powerful. mlflow.search_runs is MLflow's query API: you name the experiment (and a sort expression like metrics.f1 DESC), and it hands back real run objects exposing .info, .data.params, .data.metrics, and .data.tags. With output_format="list" you get a Python list, ready to format. The early exit is just courtesy: if the experiment was never created, return an empty list instead of querying nothing.

The print_compare_table formatter in cli.py is unchanged in spirit — the same ranked table as Lesson 2.1, now fed from a database query:

terminal
uv run flight-delays compare run_id max_iter random_state accuracy f1 1643977400e743df9a8ef37e15bd6cd4 500 7 0.8966 0.7441 324af2d64480473a848b05418a2b30a1 500 42 0.8952 0.7415

The winner is the same as in Lesson 2.1 — the run with random_state=7 wins on F1 again. Because the pipeline is deterministic, the metrics reproduce exactly; only the run ids are new. The five-piece record is intact, just stored somewhere a query can reach it.

6The UI: browse the history like you mean it

The overview Lesson 2.1 lacked arrives as a web page.

A terminal table answered "which run was the best?"; it still struggles with "show me all runs as a page I can click, with plots". MLflow ships a browser UI that reads the same store. Start it in its own terminal window, from CODE/:

terminal
uv run --locked mlflow server --backend-store-uri sqlite:///mlflow.db [MLflow] Security middleware enabled with default settings (localhost-only). To allow connections from other hosts, use --host 0.0.0.0 and configure --allowed-hosts and --cors-allowed-origins. INFO: Uvicorn running on http://127.0.0.1:5000 (Press CTRL+C to quit)

--backend-store-uri sqlite:///mlflow.db tells the server which store to read — it is exactly the file your runs write, so the UI shows precisely what run records. Two practical notes:

  • Run it from CODE/. The URI here is a relative path. Our CLI resolves mlflow.db to the lesson's absolute path from config.py; the server resolves it against the folder you launched from. Launch from CODE/ and both point at the same file.
  • The terminal is now the server's. It stays busy (that is the signal to keep it running) until Ctrl+C. Use a separate terminal window for training commands while it runs.

Open http://localhost:5000 and click the flight-delays experiment: both runs appear, best F1 first. Click one and the run page shows exactly our five pieces — a Params table, a Metrics table, a Tags list including data_sha256 and git_commit, and under Artifacts the model/model_2025_01.joblib we no longer dare overwrite. The comparison view adds the metric-versus-metric plots. The lines the server printed before "Uvicorn running" are startup notices — most usefully, it only listens on your machine by default — not errors.

That server, by the way, is the entire "tracking server" idea: a small web application that serves your tracking store over HTTP. For solo work it serves your mlflow.db; a team would run one shared store and everyone's runs would land in the same experiment. Same commands, one shared database.

Try it

Push the history further, then read it three ways. Run uv run --locked flight-delays run --max-iter 1000; in the UI, the new run appears in the experiment with its own id, and its Tags still include data_sha256 and git_commit — provenance is now automatic per run. Then re-rank without retraining: uv run --locked flight-delays compare --sort-by accuracy and watch the ordering flip. Finally, open mlflow.db in a tool that reads SQLite (or just ls mlruns) to confirm the mirrored artifacts/model/ copy exists for every run you recorded.

Takeaways
  • MLflow Tracking is four things at once: a database (the tracking store), a folder (the artifact store), a Python API (log_*, search_runs), and a web UI (mlflow server). One tracking URI points all of them at the same history.
  • Lesson 2.1's five pieces map onto MLflow's schema: params, metrics, artifact, and the fingerprints we compute become tags. The concept outlives the tool.
  • search_runs replaced our hand-rolled reader. A query API is the durable part — the store owns its schema, so nothing of ours needs to stay in sync.
  • A database must be treated like one: mlflow.db holds your whole history. It is git-ignored on purpose, and it is the file you would back up (or copy to L2.3's next steps).
  • MLflow lets solo work be additive: metrics that reproduced in L2.1 now reproduce in the database, and the model file is never silently overwritten again.
Before the next lesson — what still hurts?

The runs now live in a searchable database, ranked and browsable. Three cracks are visible if you squint:

  • Nothing says which run is the model. compare ranks runs, but the store has no idea that "the winning F1 run" is special, that it has a name, or that it is the one to serve. Promotion is still a human decision, and the artifact is still just a file path. Lesson 2.3 gives a chosen run a registered, named, versioned identity.
  • The 100 MB CSV is fingerprinted, not versioned. "same sha256" means the file happened to be sitting in data/; nothing records its history or pins a specific copy to a run. The shape of that fix is data versioning, later in the journey.
  • Writer and reader assume one machine. We started the server locally because the database is local — the moment the history must be shared, the store has to live somewhere reachable, which is a deployment problem this module's later lessons make routine.

Lesson 2.3 takes the winning run and stops treating it as a row in a table.
