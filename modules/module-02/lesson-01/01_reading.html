Tracking Fundamentals

Your models get better, you run training again and again — and every run forgets itself. This lesson gives the flight-delay project a memory: each training run records its parameters, its metrics, its saved artifact, and the data and code that produced it — in one machine-readable line you can compare.

CODE/
Before you start

You need Lesson 1.5 complete: in that lesson's CODE/ folder, uv run flight-delays logs accuracy: 0.8952 and f1: 0.7415, and the 64-test suite is green. The shared flight-delays CSV still lives in the data/ folder at the repository root.

What you'll do in this lesson

  • Give the command line tuning knobs — --max-iter and --random-state — so runs can actually differ and be worth comparing.
  • Add a small run recorder that writes one machine-readable JSON line per completed run: parameters, metrics, artifact path, data fingerprint, and code + environment fingerprint.
  • Keep each run's trained artifact recoverable under its own run id instead of being overwritten.
  • Add a compare command that answers "which run was the best?" from the recorded history.
  • Keep the full test suite and the quality gates green with the new tracking module covered.

1A run that disappears

The symptom this lesson fixes: after training, the only trace of a run is a log line that scrolls away.

Lesson 1.5 left you with a polished single step: uv run flight-delays loads the CSV, trains, evaluates, saves models/model_2025_01.joblib, and prints two numbers. Now imagine doing what an ML practitioner actually does next — tuning. You run training three times with different seeds and iteration limits, watching accuracy and F1 climb. Try to answer these questions on Tuesday morning:

  • Which of yesterday's runs produced the model file that is now on disk?
  • What parameters and score did that winning run have? What were the losing runs?
  • Which CSV and which version of the code was each run trained on?

You cannot answer any of them. The log printed the metrics once and they are gone; the file model_2025_01.joblib has a fixed name, so every run overwrote the previous one; and nothing paired a metric with the data snapshot or code revision it came from. This is the classic machine-learning failure called lost experiments. Before this course taught any of it, losing an experiment was the working definition of not being able to reproduce a model.

The engineering answer is experiment tracking: give every training run a durable, comparable record so that the question "which run was the best?" stops being a memory and becomes a query. This lesson builds the smallest honest version of that record by hand — the concept first, the purpose-built tool in Lesson 2.2.

2The run record: what "remembering a run" means

Five pieces of data turn a training attempt into a recoverable experiment.

Call one pipeline execution a run. A run is recoverable and comparable only if its record answers five questions. Everything else in this lesson is a mechanism for answering them:

  • Parameters — the settings you chose before training: max_iter, random_state, test size. Two runs differ because their parameters differ.
  • Metrics — the numbers you measured after: accuracy and F1 on the test split.
  • Artifact — the trained model file a run produced, kept under the run's own identity so it is not overwritten.
  • Data identity — a fingerprint of the exact CSV bytes used, because the same code and parameters on a different dataset are a different experiment.
  • Code + environment identity — the code revision plus the Python and library versions, so you can rebuild the same conditions later.

Skills you already own from Module 1 make this possible without a new tool: a fixed column of numbers goes into a structured file (L1.2's configuration and command contracts), the run's identity lives in a small object (L1.3), and a machine-readable line replaces the print (L1.4's logging mindset, applied to a file). The tool question comes later; first the record itself.

3Tuning knobs: how runs differ

The command line grows two flags and a subcommand, so the pipeline can be asked to vary.

Nothing is worth tracking while every run is identical. The model's solver length and seed sit as constants in config.py; to tune them you edit a line, rerun, edit again — exactly the fragility Module 1 removed. Before one run can differ from the next, the command itself must accept variation.

A command line is more than the command. Words typed after it are arguments: in uv run flight-delays run --random-state 7 the shell hands the tool extra tokens to do with as it pleases. The flight-delay CLI currently ignores all of them — it is one fixed recipe. This lesson gives it the two kinds of arguments every professional CLI uses, and both are standard practice:

  • A flag — a named option that takes a value: --random-state 7. Flag present → that value wins; flag absent → the default applies.
  • A subcommand — the first word that selects a behavior: run and compare. One program, several behaviors.

You do not write a parser by hand to read arguments. argparse is Python's standard library for exactly this: you declare the contract — option names, value types, defaults, help text — and it hands the parsed values back to you. Each option is one add_argument declaration:

src/flight_delays/cli.py (excerpt)
run_parser = subparsers.add_parser( "run", help="train the pipeline and record the run (default command)" ) run_parser.add_argument( "--max-iter", type=int, default=MAX_ITER, help="solver iterations (default: %(default)s)", ) run_parser.add_argument( "--random-state", type=int, default=RANDOM_STATE, help="random seed for the train/test split and model (default: %(default)s)", ) compare_parser = subparsers.add_parser( "compare", help="list recorded runs, best metric first" ) compare_parser.add_argument( "--sort-by", choices=["f1", "accuracy"], default="f1", help="metric used to order the runs (default: %(default)s)", )

Read one declaration and you can read them all. "--max-iter" is the name a user types. type=int is a conversion contract: terminals pass strings, so the shell delivers "1000", not the number 1000, and argparse converts it before your code ever runs — which also means --max-iter oops fails with a clean error at startup instead of crashing mid-train. default=MAX_ITER is the value used when the flag is absent. help is the descriptive line shown to a curious user, and %(default)s renders the current default into it. The user's choice finally lands at args.max_iter — argparse turns the option name into an attribute, dashes becoming underscores. --sort-by adds one more tool: choices=[...] restricts the value to a fixed list, so a typo like --sort-by accuracy1 is rejected rather than silently ignored.

Because argparse holds the whole contract, it can print it. Ask the tool about itself:

terminal
uv run flight-delays --help
output
usage: flight-delays [-h] {run,compare} ... Train, record, and compare flight-delay model runs. positional arguments: {run,compare} run train the pipeline and record the run (default command) compare list recorded runs, best metric first options: -h, --help show this help message and exit

Notice that options bind to their subcommand: --sort-by exists only on compare, so typing it after run is an error before any training starts. That is the payoff of a declared contract — the tool knows its own shape and rejects nonsense early. With no subcommand at all, the CLI falls through to run, so a bare uv run flight-delays still trains exactly as Lesson 1.5 taught. Passing a flag changes one run into another:

terminal
uv run flight-delays run --random-state 7 uv run flight-delays run --max-iter 1000

With flags and subcommands, experiments are expressible in one line — and at last distinguishable. Identical commands mean nothing to a record; differences are the whole point, and the recorder in Section 4 exists to write them down.

4The recorder: one JSON line per run

A tiny object that appends each completed run to a machine-readable file.

A log entry is for humans and scrolls away. A run record is for tools, so it must be parseable: one object per line, in JSON, appended to a file called runs/runs.jsonl.

src/flight_delays/tracking.py (excerpt)
class RunRecorder: """Append one JSON line per recorded run and read the runs back.""" def record(self, params, metrics, artifact, data, code, started_at): run_id = started_at.strftime("%Y%m%d_%H%M%S_%f") self.runs_dir.mkdir(parents=True, exist_ok=True) run_artifact = self.runs_dir / f"runs_{run_id}.joblib" shutil.copyfile(artifact, run_artifact) run = { "run_id": run_id, "started_at": started_at.isoformat(), "params": params, "metrics": metrics, "artifact": str(run_artifact), "data": data, "code": code, } line = json.dumps(run, sort_keys=True, separators=(",", ":")) with self.runs_file.open("a", encoding="utf-8") as handle: handle.write(line + "\n") return run

Three details make this a record, not a log:

  • A run id. The timestamp with microseconds becomes the run's identity (20260911_120340_694107). Everything else in the record can point back to that id.
  • An artifact that survives. shutil.copyfile copies the freshly trained pipeline into runs/runs_<run_id>.joblib under the run's own name, so run N+1 never overwrites run N. The production file models/model_2025_01.joblib still updates as before — both exist, with different jobs.
  • One object per line. JSON Lines (JSONL) appends without locking or rewriting; any tool — a text editor, a script, compare — can read the file line by line. The file is machine-readable exactly because it is one object, not a paragraph.

In cli.py, main() calls the recorder just after save_model(). Metrics are converted to plain float first — scikit-learn returns NumPy float64 values, which JSON cannot serialize — and are stored at full precision, even though the log prints them rounded:

src/flight_delays/cli.py (excerpt)
raw_metrics = evaluate_model(fitted, X_test, y_test) metrics = {name: float(value) for name, value in raw_metrics.items()} resolved_model_dir.mkdir(parents=True, exist_ok=True) model_path = save_model(fitted, resolved_model_dir / MODEL_FILE) run = RunRecorder(resolved_runs_dir).record( params=snapshot_params( max_iter=max_iter, random_state=random_state, test_size=TEST_SIZE ), metrics=metrics, artifact=model_path, data=data_fingerprint(csv_path), code=code_fingerprint(), started_at=started_at, )

Open runs/runs.jsonl after one training run and you will find a single line like this one (formatted here for reading; on disk it is one line, and artifact paths are absolute on your machine):

runs/runs.jsonl (recorded run, shown wrapped)
{"run_id": "20260911_120340_694107", "started_at": "2026-09-11T12:03:40.694107+00:00", "params": {"max_iter": 500, "random_state": 42, "test_size": 0.2}, "metrics": {"accuracy": 0.8951500181898252, "f1": 0.7414786139174772}, "artifact": "runs/runs_20260911_120340_694107.joblib", "data": {"file": "flight_delays_2025_01.csv", "sha256": "ed6d5b115c59aa9c"}, "code": {"git_commit": "8ffdf11", "git_dirty": true, "python_version": "3.12.11", "dependencies": {"joblib": "1.6.0", "numpy": "2.5.3", "pandas": "3.0.5", "scikit-learn": "1.9.0"}}}

Every one of the five questions from Section 2 is now answered by this single object. And because the metrics are stored at full precision, later comparisons never lose the fourth decimal to a rounded log line.

5Provenance: fingerprints, not names

Content hashes for the data, and a code + environment stamp for everything else.

Names lie; bytes do not. Two CSV files can both be called flight_delays_2025_01.csv while holding different rows, so a run record that says "the file I used" proves nothing. Identity must come from the content itself — and that is exactly what a hash function provides.

A hash function takes data of any size and returns a short, fixed-size string called a digest. SHA-256 ("Secure Hash Algorithm", 256 bits) returns 64 hexadecimal characters. Three properties make it perfect for identity:

  • Deterministic — the same bytes always give the same digest. You compare a few characters instead of streaming 100 MB twice.
  • Sensitive — change one character and nearly every digest character changes (the "avalanche effect"). Equal digests are strong evidence the contents are byte-for-byte identical.
  • One-way — the digest cannot be turned back into the data. It is a fingerprint: it identifies a person but never lets you reconstruct them.

Watch the second property in a live REPL — adding one character flips most of the preview:

terminal
>>> hashlib.sha256(b"jfk-lax").hexdigest()[:16] '72348a6378c4da7e' >>> hashlib.sha256(b"jfk-lax!").hexdigest()[:16] '3a509acd20b6a6b3'

The flight-delay identity is this same hash computed over the whole CSV, truncated to the first 16 characters:

src/flight_delays/tracking.py (excerpt)
def data_fingerprint(path: Path) -> dict[str, str]: """Return the file name and a short SHA-256 of its bytes.""" digest = hashlib.sha256() with path.open("rb") as handle: for chunk in iter(lambda: handle.read(1 << 16), b""): digest.update(chunk) return {"file": path.name, "sha256": digest.hexdigest()[:16]}

The file is hashed in small chunks rather than all at once: Python reads a 64 KiB window — 1 shifted left by 16 bits is 65536 bytes — feeds it into the digest, and repeats until the file ends, so a 100 MB CSV never has to fit in memory. A few hundred milliseconds of hashing buys an honest answer to "which dataset trained this model?" When you record the digest on Tuesday, you can re-hash any CSV later and know instantly whether it is the same dataset — no relying on memory, no trusting a file name.

Code and environment get the same treatment. The run stamps the short git commit it started from, whether the working tree was dirty (uncommitted changes can alter the result!), the Python version, and the installed versions of the four core libraries:

src/flight_delays/tracking.py (excerpt)
def git_fingerprint() -> dict[str, str | bool]: """Return the short commit and dirty flag, or a clear "<none>" fallback.""" try: commit = subprocess.run( ["git", "rev-parse", "--short", "HEAD"], check=True, capture_output=True, text=True, timeout=5, ).stdout.strip() dirty = bool( subprocess.run( ["git", "status", "--porcelain"], check=True, capture_output=True, text=True, timeout=5, ).stdout.strip() ) return {"git_commit": commit, "git_dirty": dirty} except (subprocess.SubprocessError, OSError): return {"git_commit": "<none>", "git_dirty": False}

Together these stamps are the reproduction chain: code + environment + data. The lesson's machine-readable record can now answer the deeper question too — "can I rebuild Tuesday's winning model at all?" The commit says which code; the dependency versions say which libraries; the digest says which data. If any of the three changes, the record signals that the run was a different experiment.

6Compare: naming the best run

Reading the history back, sorted by the metric that matters.

A recorder without a reader would take you to a terminal and a JSON file to eyeball. The compare subcommand is the reader: it loads every recorded run, orders them by one metric, and prints a table with the best on top:

src/flight_delays/tracking.py (excerpt)
def compare_runs(runs_dir: Path, sort_by: str = "f1") -> list[dict[str, object]]: """Return recorded runs sorted by one metric, best first.""" runs = RunRecorder(runs_dir).runs() def metric_value(run: dict[str, object]) -> float: metrics = cast(dict[str, float], run["metrics"]) return float(metrics[sort_by]) return sorted(runs, key=metric_value, reverse=True)

The full history lives in the single run_id-keyed, time-ordered file, so ordering is a sort, not a trick. On your machine after two runs, uv run flight-delays compare prints something like this (your run ids are timestamps and will differ):

output
run_id max_iter random_state accuracy f1 20260911_120353_162694 500 7 0.8966 0.7441 20260911_120340_694107 500 42 0.8952 0.7415

The random-state-7 run won on both metrics, and its winner's artifact is runs/runs_20260911_120353_162694.joblib — still on disk, still loadable, because every run keeps its own copy. "Which run was the best?" now has a command that answers it.

7Run it — the milestone

Every training run writes a recoverable record, and compare reads it back.

Open this lesson's CODE/ folder and start with the suite from Lesson 1.5, now grown with tracking tests:

terminal
uv sync --locked uv run --locked pytest
output (tail)
src/flight_delays/tracking.py 68 4 94% 58-59, 68-69 src/flight_delays/train.py 10 0 100% src/flight_delays/validate.py 19 0 100% ---------------------------------------------------------- TOTAL 261 12 95% 77 passed in 1.96s

77 tests, including the new test_tracking.py for fingerprints, recording, and ordering. Then run the pipeline twice — the default, and one genuinely different run:

uv run --locked flight-delays run uv run --locked flight-delays run --random-state 7

Same data, same code, different seed — and both runs now exist side by side. The default run still holds the Lesson 1.5 numbers (0.8952 / 0.7415), the second is a small improvement (0.8966 / 0.7441), and compare proves the winner is a fact, not a feeling:

terminal
uv run --locked flight-delays compare
output
run_id max_iter random_state accuracy f1 20260911_120353_162694 500 7 0.8966 0.7441 20260911_120340_694107 500 42 0.8952 0.7415

Finish with the Module 1 quality gates — they must stay green with the new module and tests:

terminal

All green. That is the milestone: every completed run is now recorded at full precision, each with its own artifact and its data + code fingerprints, and compare reads the history back in ranked order. "Which run was the best?" no longer depends on anyone's memory.

Try it

Because tuning knobs now exist, hunt for the best logistic-regression run: try --max-iter 1000 and a couple more seeds, then run compare and read which run won. Look at runs/runs.jsonl in an editor and confirm every new line keeps the same shape — same keys, same nesting. Then prove recoverability: pick the top run’s run_id, load its artifact in one line, and check that predicting the first test row gives the same probability the run logged:

terminal
uv run python -c "from flight_delays.predict import FlightDelayModel; from flight_delays.config import MODEL_INPUT_COLUMNS; import pandas as pd; from pathlib import Path; m = FlightDelayModel.load(Path('runs/runs_<run_id>.joblib')); print(m.predict_delay(pd.read_csv(r'..\..\..\..\data\flight_delays_2025_01.csv').head(1)[list(MODEL_INPUT_COLUMNS)])[0])"
Takeaways
  • A run record is the answer to "which run was the best?": parameters (what you chose), metrics (what you measured), artifact (what you saved), and provenance (data + code + environment).
  • Params and knobs come first — a pipeline with only constants produces identical runs and nothing to track.
  • Content hashes, not names, identify data. A SHA-256 fingerprint catches silently changed CSVs that a file name would hide.
  • Records are for tools: one JSON object per line is machine-readable, appendable, and sortable — the file runs/runs.jsonl is your whole history.
  • Each run keeps its own artifact copy, so "recover the winning model" is a file path, not an archaeology project.
Before the next lesson — what still hurts?

The hand-rolled tracker works, and it is exactly as small as a hand-rolled tracker must be. Its limits will start to bite the day runs multiply:

  • The JSONL schema is yours alone: metric names, key ordering, and grouping must be kept consistent by hand, and no overview page or chart exists — comparing ten runs means re-reading a terminal table.
  • Recording is a call we added inside main(); nothing yet attaches a run to an experiment, a notebook, or a tag like "feature_experiment".
  • Artifacts pile up in a folder with no notion of a registry — which run is currently the serving model, and how it got promoted, is again a human memory.

Lesson 2.2 brings in a dedicated tool that professionalizes exactly this tracker — runs, metrics, params, artifacts, and a comparison UI.
