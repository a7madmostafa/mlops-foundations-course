Automated Testing

Every change to the pipeline is a gamble until something proves the behavior stayed right. This lesson adds a fast pytest suite that checks cleaning, validation, the command boundary, the prediction contract, and the complete chain.

CODE/
Before you start

You need Lesson 1.4 complete: in that lesson's CODE/ folder, uv run flight-delays logs accuracy: 0.8952 and f1: 0.7415, and ruff format --check src, ruff check src, and mypy src are all green.

What you'll do in this lesson

  • Add pytest and its coverage plugin to the project's dev dependencies.
  • Write a suite of unit tests for cleaning, data validation, and pipeline construction — each one an executable claim about one function.
  • Share test data through fixtures, and check many inputs with parametrized cases instead of copy-pasted assertions.
  • Pin raw-input, output-shape, probability-range, and class-1 meaning contracts; then prove the full chain and command boundary work.
  • Read a coverage report that tells you exactly what is — and is not — exercised, and deal honestly with its limits.

1Every change is a gamble

The symptom this lesson fixes: nothing proves the pipeline still works after you touch it.

Lesson 1.3 moved feature derivation into the saved pipeline and clarified the code contracts, while Lesson 1.4 added validation and logging. Both promised the successful model behavior stayed the same. But without automated tests, your only proof was still: re-run, eyeball the numbers, hope.

Now make it concrete. Suppose you "improve" clean_flights() in Lesson 1.4's src/flight_delays/clean.py — for example you decide to also drop extreme departure delays. You run uv run flight-delays and the log prints accuracy: 0.8941 instead of 0.8952. Questions you cannot answer from a log line:

  • Is 0.8941 the intended consequence of your change, or a bug you just introduced?
  • Did you accidentally break the hour derivation, the row filter, or the split?
  • Was the model file even written? Did prediction agree with training?

Manual verification does not scale: as a project grows, a human eye on two decimal places is neither fast enough nor complete enough. The engineering answer is automated testing: check intended behavior with code, so a change that breaks it fails loudly in a fraction of a second, before any human has to look. The full set of tests, run together as one command, is called a suite. "It still works" stops being a hope and becomes a suite you can run.

2The first test — an executable claim

Assertions, unit tests, and how pytest finds them.

Start from the smallest useful piece. clean_flights() has a rule raw data must obey: cancelled and diverted flights never enter the modeling cohort. Write that rule down as a test:

tests/test_clean.py (first test)
"""Cleaning unit tests — row filters and the derived hour column.""" import pandas as pd import pytest from flight_delays.clean import clean_flights from flight_delays.config import TARGET def test_clean_keeps_only_completed_flights() -> None: df = pd.DataFrame( { "Cancelled": [0, 1, 0], "Diverted": [0, 0, 0], "CRSDepTime": [900, 600, 2130], TARGET: [0, 0, 1], } ) flights = clean_flights(df, target=TARGET) assert len(flights) == 2 assert (flights["Cancelled"] == 0).all()

Three new ideas fit on those lines:

  • Assertion — a statement that a condition must be true. Python's assert raises AssertionError when the condition is false. A test is literally a function whose assertions must hold.
  • Unit test — a check of one small function in isolation: give it crafted input, call it, and assert on the output. No filesystem, no network, no full pipeline.
  • Test discovery — pytest's matching rule: collect every function named test_* from every file named test_*.py and run them one by one. The name test_clean_keeps_only_completed_flights is half the plumbing: no registration, no if __name__ == "__main__". Name it right and pytest finds it.

The test is also a claim: "when I clean a frame with one cancelled flight, I get back exactly the two completed ones." If a future edit to clean_flights() keeps cancelled rows, this test turns red and names the function that broke. That is the entire value proposition: the suite is a written-down, self-checking version of the behavior you promised.

Make pytest part of the project before running anything. Add pytest and pytest-cov to the dev group of pyproject.toml (the coverage plugin pays for itself in a later step), plus a small pytest configuration:

pyproject.toml (excerpt)
[dependency-groups] dev = [ "ruff>=0.9", "mypy>=1.14", "pandas-stubs>=2.2", "pytest>=8.3", "pytest-cov>=6.0", ] [tool.pytest.ini_options] testpaths = ["tests"] addopts = "--cov=flight_delays --cov-report=term-missing"

testpaths tells pytest where to look; addopts makes coverage part of every pytest run, so the two-mile-high milestone — tests and a coverage report in one command — becomes the default. Then install and run:

terminal
cd modules/module-01/lesson-05/CODE uv sync uv run pytest

pytest prints one dot per passed test and counts the total. At this point, right after writing the single test above, a run would look like this (the lesson's completed CODE/ suite reports 64 tests):

output (the first test only)
collected 1 item tests/test_clean.py . [100%] =========================== 1 passed ==========================

3Arrange–Act–Assert, and failure as an assertion

The anatomy of a readable test, and turning L1.4's raise into a check.

Read any good test as three movements — Arrange, Act, Assert:

  • Arrange — build the inputs: the crafted DataFrame, the temp file, the model.
  • Act — call the thing under test: clean_flights(df, ...), ensure_columns(df, ...).
  • Assert — declare what must be true of the result.

That first test_clean test was exactly these three, reading top to bottom. Keeping them distinct makes the test a story: when the assertion fails, you know the act line produced something surprising — you do not have to re-read the whole file.

Lesson 1.4's validate.py raises exceptions on expected breakage. Now a missing column is not a crash sitting under a log line — it is a contract to pin. The Assert movement has to say: this call MUST raise, and with this type. pytest's pytest.raises context manager is that assertion:

tests/test_validate.py (excerpt)
def test_ensure_columns_raises_naming_exactly_the_missing_columns( raw_flights: pd.DataFrame, raw_columns: list[str], missing: list[str], ) -> None: df = raw_flights.drop(columns=missing) with pytest.raises(ValueError) as excinfo: ensure_columns(df, raw_columns) message = str(excinfo.value) assert "missing required columns" in message for column in missing: assert column in message

The block form of pytest.raises(ValueError) fails the test if no ValueError is raised. So this test fails in two different, both useful ways: if ensure_columns() stops raising (the missing column turns into a silent KeyError somewhere later), the test catches it; if the message stops naming the exact missing columns, the test catches that too. The exception's message text is behavior worth pinning — Lesson 1.4 spent real effort making it specific, and now that effort is guaranteed to stay.

You will also see tmp_path in tests that touch the filesystem (like the two lines above). It is one of pytest's built-in fixtures: every test that asks for it receives a fresh temporary directory as a pathlib.Path, removed automatically afterwards. Writing a fake CSV into tmp_path tests file handling without ever polluting the project folder.

Notice the test calls raw_flights.drop(columns=missing) to create a bad frame. Tests feed deliberately broken inputs to confirm the guard rails; the happy path gets its own assertions elsewhere. That is what "schema test" means for a data pipeline: you test that clean data passes and that each kind of dirty data fails loudly.

4Fixtures: test data without the CSV

Reusable inputs, so tests never depend on the downloaded dataset.

The first test built its DataFrame inline — fine for one test, copy-paste misery for twenty. Cleaning tests, validation tests, and the integration test all need a raw frame; tests that train a model need feature data; tests of the prediction contract need a fitted model. Duplicating all of that makes the suite unreadable and easy to break in one copy and not another.

pytest's answer is the fixture: a named function that prepares an object and injects it into every test that asks for it. The default scope creates a fresh value for each test. A fixture marked scope="session" is created once for the entire suite. Shared fixtures live in tests/conftest.py, which pytest discovers automatically:

tests/conftest.py (excerpt)
@pytest.fixture def raw_flights() -> pd.DataFrame: """A tiny raw frame mirroring the real CSV's shape. Six rows: one cancelled (index 2), the rest completed and non-diverted. Columns are exactly the raw schema the pipeline validates against. """ return pd.DataFrame( { "Cancelled": [0, 0, 1, 0, 0, 0], "Diverted": [0, 0, 0, 0, 0, 0], "CRSDepTime": [900, 2130, 600, 0, 2300, 1505], "DepDelay": [-3, 12, 5, 0, -7, 30], "Distance": [180, 900, 340, 120, 2500, 55], "CRSElapsedTime": [40, 150, 75, 30, 320, 15], "DayOfWeek": [1, 2, 3, 4, 5, 6], "Reporting_Airline": ["AA", "DL", "UA", "AA", "WN", "DL"], "Origin": ["JFK", "ATL", "ORD", "JFK", "LAX", "SFO"], "Dest": ["LAX", "MIA", "DFW", "BOS", "ORD", "SEA"], TARGET: [0, 1, 0, 0, 0, 1], } )

Why build fake data at all instead of reading the real CSV? Three reasons that matter from day one:

  • The suite must run without the dataset. The flight-delays CSVs are downloaded separately (they are git-ignored). On a fresh clone, a test that reads the real CSV fails before it checks anything. The suite should pass with tests/ alone.
  • Speed and determinism. The real file is 100 MB and training takes seconds. Six rows clean in microseconds; the synthetic modeling set is seeded, so every run is identical. A suite you run often has to be cheap.
  • Precision. Hand-built data tests exactly the edge you mean: a cancelled row, a missing column, or an invalid time such as 2400.

The small raw_flights fixture keeps its default function scope so mutations cannot leak between tests. The 300-row raw_training_flights and fitted_model fixtures use session scope because building and fitting them is more expensive and their tests treat them as read-only.

5Parametrization: one test, many inputs

Turn every "and also this case" into data, not more test code.

The saved model derives an hour from a valid HHMM value, while validation rejects impossible times. Do you want a copy-pasted test for every boundary? No — run the same test with a table of inputs. That is parametrization:

tests/test_features.py (excerpt)
@pytest.mark.parametrize( "raw_time,expected_hour", [ (0, 0), (5, 0), (859, 8), (900, 9), (2359, 23), ], ) def test_add_scheduled_departure_hour_from_valid_hhmm( raw_time: int, expected_hour: int, ) -> None: raw = pd.DataFrame({"CRSDepTime": [raw_time]}) features = add_scheduled_departure_hour(raw) assert features.loc[0, "scheduled_departure_hour"] == expected_hour

@pytest.mark.parametrize declares the argument names and a list of value tuples; pytest runs the test once per tuple and reports each case separately:

output (excerpt)
tests/test_features.py::test_add_scheduled_departure_hour_from_valid_hhmm[0-0] PASSED tests/test_features.py::test_add_scheduled_departure_hour_from_valid_hhmm[859-8] PASSED tests/test_features.py::test_add_scheduled_departure_hour_from_valid_hhmm[2359-23] PASSED

Parametrize along the axis that varies. Here that is the valid raw time and expected hour. A separate parametrized validation test states that 1260, 2400, 2500, negative, fractional, and nonnumeric values are rejected.

6Testing ML code: schema checks and the prediction contract

ML code is hardest to test by "score goes up" — so pin the contracts, not the numbers.

Your instinct might be to assert accuracy == 0.8952. Exact equality is usually brittle when data, dependencies, or training settings change. Fixed reference datasets and threshold-based regression tests can be useful later, but this beginner suite first pins the stable code contracts:

tests/test_model.py (excerpt)
def test_saved_model_round_trips_through_load( fitted_model, tmp_path: Path, flights_xy, ) -> None: X, _ = flights_xy path = save_model(fitted_model, tmp_path / "model.joblib") loaded = FlightDelayModel.load(path) before = FlightDelayModel(fitted_model).predict_delay(X.iloc[:5]) after = loaded.predict_delay(X.iloc[:5]) np.testing.assert_allclose(before, after) @pytest.mark.parametrize("n_rows", [1, 3, 10]) def test_predict_delay_returns_one_probability_per_row( fitted_model, flights_xy, n_rows: int, ) -> None: X, _ = flights_xy probabilities = FlightDelayModel(fitted_model).predict_delay(X.iloc[:n_rows]) assert probabilities.shape == (n_rows,) def test_predict_delay_probabilities_stay_in_the_unit_interval( fitted_model, flights_xy, ) -> None: X, _ = flights_xy probabilities = FlightDelayModel(fitted_model).predict_delay(X.iloc[:10]) assert probabilities.min() >= 0.0 assert probabilities.max() <= 1.0 def test_predict_delay_returns_the_positive_class_probability( fitted_model, flights_xy ) -> None: X, _ = flights_xy rows = X.iloc[:5] delayed_column = int(np.flatnonzero(fitted_model.classes_ == 1)[0]) expected = fitted_model.predict_proba(rows)[:, delayed_column] actual = FlightDelayModel(fitted_model).predict_delay(rows) np.testing.assert_allclose(actual, expected)

Three ML-specific contracts are being pinned here, and each one targets a real failure mode:

  • The round trip. Save then load must give identical predictions. A joblib version bump or a change to save_model() that writes the wrong artifact would break this on the spot.
  • The shape contract. Predictions are per row: three rows in, three probabilities out.
  • The range contract. predict_delay promises probabilities, meaning values in [0, 1]. A pipeline change that starts returning raw logits (which can be any real number) breaks this immediately — and a caller downstream who thresholds at 0.5 would be silently wrong.
  • The meaning contract. Shape and range alone cannot distinguish delayed-class probabilities from on-time-class probabilities. The semantic test locates class 1 and compares the wrapper with that exact column.

The schema tests in tests/test_config.py are the same idea one level up: MODEL_INPUT_COLUMNS contains raw CRSDepTime, while engineered scheduled_departure_hour stays in FEATURES. A list changed in one place and forgotten in another becomes a loud failure.

7Pipeline integration: the chain as one

Unit tests check each link; an integration test proves the chain is a chain.

Unit tests zoom in on single functions. But the project's promise lives in the composition: raw frame in, clean it, validate it, split, build, train, evaluate, save, load, predict. Each piece is unit-tested, yet the seams between them might still disagree — the classic being "the column order the predictor expects differs from what cleaning produces." The integration test runs the whole chain on synthetic data, using the real modules, exactly as cli.py does:

tests/test_pipeline.py (excerpt)
def test_pipeline_clean_to_predict_on_synthetic_data( raw_training_flights: pd.DataFrame, tmp_path: Path, ) -> None: cleaned = clean_flights(raw_training_flights, target=TARGET) ensure_columns(cleaned, MODEL_INPUT_COLUMNS + [TARGET]) ensure_nonempty(cleaned, target=TARGET) X = cleaned[MODEL_INPUT_COLUMNS] y = cleaned[TARGET] X_train, X_test, y_train, y_test = train_test_split( X, y, test_size=TEST_SIZE, random_state=RANDOM_STATE, stratify=y ) model = build_model(NUMERIC_FEATURES, CATEGORICAL_FEATURES) fitted = train_model(model, X_train, y_train) metrics = evaluate_model(fitted, X_test, y_test) assert set(metrics) == {"accuracy", "f1"} assert 0.0 <= metrics["accuracy"] <= 1.0 model_path = save_model(fitted, tmp_path / "model.joblib") served = FlightDelayModel.load(model_path) probabilities = served.predict_delay(X_test.iloc[:5]) assert probabilities.shape == (5,) assert probabilities.min() >= 0.0 assert probabilities.max() <= 1.0

Run it with uv run --locked pytest -v tests/test_pipeline.py. One raw synthetic dataset stays in the chain through loaded-model prediction. A separate test_cli.py calls main() with temporary data and model paths, so the command boundary is tested without touching the real course files.

8Coverage: a report that tells the truth

How much of the code actually ran — and why the headline number is not the whole story.

Coverage answers one narrow, precise question: of all the executable source lines, which ones actually ran during the suite? Because --cov is now a pytest default, every run ends with a table:

output
Name Stmts Miss Cover ----------------------------------------------- src/flight_delays/__init__.py 0 0 100% src/flight_delays/__main__.py 2 2 0% 3-5 src/flight_delays/clean.py 4 0 100% src/flight_delays/cli.py 54 1 98% 122 src/flight_delays/config.py 15 0 100% src/flight_delays/evaluate.py 6 0 100% src/flight_delays/features.py 17 0 100% src/flight_delays/load.py 4 0 100% src/flight_delays/log_setup.py 6 0 100% src/flight_delays/predict.py 22 0 100% src/flight_delays/train.py 10 0 100% src/flight_delays/validate.py 19 0 100% ----------------------------------------------- TOTAL 159 3 98%

Most logic is covered, including CLI orchestration and logging setup. The only deliberately uncovered module is the two-line __main__.py launcher; calling python -m flight_delays would only repeat the already-tested run() call.

The 98% headline is useful but incomplete. Coverage measures which lines ran, not whether behavior is verified. Three facts matter:

  • 100% coverage does not mean "no bugs". A line can run and still compute something wrong; coverage is blind to correctness.
  • Temporary paths let command tests exercise files and artifacts without mocking or polluting the repository.
  • This suite avoids exact score equality. A fixed reference dataset can support a useful threshold or regression check later, but 0.8952 is not a universal constant.

Coverage is a radar, not a gate: it shows you which blind spots you know about. Use it to spot code that nobody exercises at all by accident, and stay suspicious of the code that supposedly runs fine.

Takeaways
  • A unit test is an executable claim about one function: arrange inputs, call it, assert on the result. Name it test_* in a test_*.py file and pytest runs it for free.
  • Expected failure is an assertion too: pytest.raises pins the exception type and message, so a guard rail can never silently disappear.
  • Fixtures centralize reusable setup; scope controls lifetime. Parametrization makes each edge case a row in a table instead of a copied test.
  • ML tests pin contracts, not scores: probability per row, values in [0, 1], save–load identical, schema lists consistent. Metrics change on retraining; contracts should not.
  • Coverage tells you which lines ran, not whether they are correct. It is a radar — read it, treat 100% logic coverage and deliberately uncovered seams as the healthy shape.
Before the next module — what still hurts?

The suite runs only when someone remembers to run it, and it knows nothing about which data and which code version produced which model — the tests prove the code is coherent, not that any particular run is reproducible.

  • Nothing records the data, code, and parameters behind a trained artifact — "which run was the best?" has no answer → Module 2 starts by recording experiments and their inputs.
  • The tests are still a command you must type; nothing prevents them from being skipped or forgotten → later, automation runs format, lint, type, and this suite on every change before anything ships.
  • Tests check the code, but nothing checks whether incoming data is drifting from the training distribution — a different failure family that these unit tests cannot detect.
