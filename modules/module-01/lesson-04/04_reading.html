Robustness & Logging

Your pipeline crashes with a wall of traceback text and prints its results to nowhere. This lesson makes it fail loudly with a clear error on expected breakage and talk with timestamped logs.

CODE/
Before you start

You need Lesson 1.3 complete: uv run flight-delays prints accuracy: 0.8952 and f1: 0.7415, and Ruff + mypy are installed and green in the lesson's CODE/ folder.

What you'll do in this lesson

  • Break the pipeline on purpose and learn to read what its traceback actually tells you.
  • Add checks for missing files, missing columns, invalid HHMM values, and empty modeling data.
  • Use raise and narrow try/except handling for expected input problems.
  • Replace print() with one shared standard-library logging setup, severity levels, timestamps, and logger names.
  • Confirm the pipeline still logs accuracy 0.8952/f1 0.7415 and Ruff + mypy stay green.

1A crash that tells you nothing

The symptom this lesson fixes, and what a traceback is for.

Open the Lesson 1.3 CODE/, run uv run flight-delays, and it works — numbers on screen. Now point the pipeline at a folder that has no CSV:

terminal
# macOS / Linux FLIGHT_DATA_DIR=/no/such/dir uv run flight-delays # Windows PowerShell $env:FLIGHT_DATA_DIR="C:\no\such\dir"; uv run flight-delays

The tail of what Python prints looks like this:

terminal
Traceback (most recent call last): File "...\src\load.py", line 10, in load_csv return pd.read_csv(path) ^^^^^^^^^^^^^^^^^ FileNotFoundError: [Errno 2] No such file or directory: '...\\flight_delays_2025_01.csv'

Do not close that window yet — it just failed in a very educational way. This printout is a traceback: a top-to-bottom list of the call frames that were active when the failure happened. Python prints it whenever an unhandled exception — its word for "something went wrong" — reaches the top of your program.

  • Exception — a signal that something went wrong at runtime. Built-in types include FileNotFoundError, ValueError, KeyError, ZeroDivisionError; each carries a message.
  • Traceback — Python's report of where the exception travelled: each frame (file + line + function), with the exception type and message on the last line.

Read the traceback correctly and the last line is the one that matters: FileNotFoundError, plus the path. The frames above tell you where the failure surfaced (load.py line 10). But notice what the message does not say: it does not tell you the CSV is missing, that it is something you can fix, or what to do about it. A colleague tasked with re-running the pipeline would have to guess.

Separate failures into two families, because they deserve different treatment:

  • Expected breakage — inputs we can predict will sometimes be wrong: the file is missing, a column is renamed, a data pull returned zero rows. These deserve a designed message: what happened + what to do.
  • Unexpected errors — a bug nobody predicted, like a column of text that should be numbers. Keep the traceback for these. It is your debugging microscope: it shows exactly which call and line blew up.

Robust means: expected failure is caught, named, and explained; unexpected failure still leaves the traceback behind for debugging. Lesson 1.3's pipeline does neither on expected breakage. It dumps raw FileNotFoundError text with no guidance, and its only voice on success is a print(). Fix both.

2Failing loudly with clear errors

Validate at the boundary and raise exceptions that say what to do.

The practice: fail fast at the boundary

Checks belong at the edge of the pipeline, right where the raw input arrives — not deep inside a training function where the original source of the problem is far away. That is the fail fast principle: stop the moment you know the input is wrong, with a message that says so.

The new src/flight_delays/validate.py checks the file, columns, row count, and scheduled-time domain. Input problems use one project-specific DataValidationError, while a missing path remains FileNotFoundError:

src/flight_delays/validate.py
"""Clear, loud checks for the data the pipeline depends on.""" from pathlib import Path import pandas as pd class DataValidationError(ValueError): """The input data violates a requirement the user can fix.""" def ensure_file_exists(path: Path) -> None: """Raise FileNotFoundError with a helpful hint if the CSV is missing.""" if not path.is_file(): raise FileNotFoundError( f"Data file not found: {path}. Download the flight-delays CSV " "first, then run again. See the download command in " "data/README.md." ) def ensure_columns(df: pd.DataFrame, required: list[str]) -> None: """Raise DataValidationError for missing columns.""" missing = [col for col in required if col not in df.columns] if missing: raise DataValidationError( f"Data is missing required columns: {missing}. " f"Found {len(df.columns)} columns instead." ) def ensure_nonempty(df: pd.DataFrame, target: str) -> None: """Raise DataValidationError if there are no modeling rows.""" if len(df) == 0: raise DataValidationError( "No modeling rows after cleaning. Check that the CSV contains " f"completed flights with a known {target} value." )

REQUIRED_RAW_COLUMNS lists columns that must exist in the CSV. ensure_scheduled_departure_times() then requires whole HHMM values from 0000 through 2359, with minutes below 60. Values such as 1260, 2400, and 2500 fail clearly instead of being silently changed.

raise FileNotFoundError("...") creates and throws an exception. The type matters: run() can handle known input problems without also swallowing an unrelated ValueError raised by model training.

The control flow: try / except / else / finally

Validating is half the fix. The other half is what the program does when a check (or any risky call) raises. Four clauses do the job:

minimal example
try: result = int(user_input) # risky step: may raise ValueError except ValueError: print("Not a number, using 0") # only on failure result = 0 else: print("Parsed a real number") # only on success finally: print("Input check finished") # always runs
  • try wraps the call that might fail.
  • except ValueError: runs only when that exception type is raised. Catch exactly what you can handle; let everything else propagate.
  • else: runs only when try completed without raising.
  • finally: always runs — success or failure — the place for cleanup.

The print() calls above are stand-ins. They fail the moment a message is not for the user but for the record — which is the next section. Keep the control-flow shape in mind; the output mechanism changes next.

3Prints are a dead end

Why print() cannot be the project's voice as it grows.

Lesson 1.3's cli.py reports success with print(f"accuracy: {metrics['accuracy']:.4f}") and failure with an unhandled traceback. That was fine for a first package. Now ask what you need from a pipeline that will be re-run on new data, by schedulers, from CI, or on servers:

  • Severity. A warning and an error are not equal. You want to filter them, and to silence the noise when good is good enough.
  • When and where. Was this from Monday's run of load or Wednesday's of train? Each message needs a timestamp and a source name.
  • Destinations. Console today, a file tomorrow, an error-tracking service later. One line of output should be re-routable without editing every call site.

print() has none of this: no levels, no timestamps, no source, no routing. The moment something is not you watching a terminal, prints are a dead end. The standard-library logging module is the replacement built into Python — nothing new to install.

Before (L1.3 print)

print(f"accuracy: {metrics['accuracy']:.4f}")

After (L1.4 logging)

logger.info("accuracy: %.4f", metrics["accuracy"])

The two lines output almost the same characters — the difference is everything around the message: it now has a level, a timestamp, a source, and a pluggable destination. An "almost identical line" staying consistent through a refactor to files, JSON, or a monitoring service is exactly the leverage you buy. Now the vocabulary:

4Logging fundamentals

Levels, loggers, handlers, and formatters — the four pieces.

The logging module has one job: emitting log records. Every record is produced with a level, tagged with a logger name, and carries a timestamp. Four concepts govern what happens next:

  • Level — severity, in increasing order: DEBUG, INFO, WARNING, ERROR, CRITICAL. Every logger has a threshold; levels below it are dropped.
  • Logger — the named channel you call: logger.info(...). Each module owns one via logging.getLogger(__name__).
  • Handler — the destination a record is sent to: console, a file, HTTP. A logger can have several; without one, nothing happens.
  • Formatter — the layout of each line: what order timestamp, level, name, and message appear in.

One logger per module

At the top of a file that will log, add one line:

src/flight_delays/cli.py (top)
logger = logging.getLogger(__name__)

__name__ is the module's import name (here flight_delays.cli). The logger name does two jobs: it appears in the output, and it is the key you reuse if you ever want to tune one module only. This is why production code creates a logger per module — one unnamed global logger loses the "which module" answer.

printf-style formatting

Notice the call replaces string interpolation with a format string plus arguments:

comparison
logger.info("accuracy: %.4f", metrics["accuracy"]) # logging idiom print(f"accuracy: {metrics['accuracy']:.4f}") # what we replace

The message string stays a template; the values are passed separately. Two reasons: the template is named and readable, and the formatting work only happens if the record is actually emitted — at DEBUG level under an INFO threshold, the expensive part never runs. Follow this idiom everywhere.

The shared setup

Any module logger feeds a shared root logger, so the whole project needs exactly one configuration place. The new src/flight_delays/log_setup.py is that place:

src/flight_delays/log_setup.py
"""Shared logging configuration for the flight-delay pipeline.""" import logging import sys LOG_FORMAT = "%(asctime)s | %(levelname)-8s | %(name)s | %(message)s" DATE_FORMAT = "%Y-%m-%d %H:%M:%S" def setup_logging(level: int = logging.INFO) -> None: """Configure the root logger once, at process start. Every module builds its own logger with ``logging.getLogger(__name__)``; this one call sets the format, level, and destination for all of them. """ logging.basicConfig( level=level, format=LOG_FORMAT, datefmt=DATE_FORMAT, stream=sys.stdout, force=True, )

basicConfig is the one-call configurator: it installs a handler on the root logger and sets the level, format string, and date format.

  • %(asctime)s — the timestamp, in the shape given by datefmt.
  • %(levelname)-8s — the level, left-justified in 8 characters, so INFO and ERROR align in a column.
  • %(name)s — the logger name (flight_delays.cli, flight_delays.load, …).
  • %(message)s — the formatted message you passed.

Decode a real line against the format string:

real output
%(asctime)s %(levelname)-8s %(name)s %(message)s 2026-09-10 16:17:23 INFO flight_delays.cli accuracy: 0.8952

setup_logging() must run before anything logs, so the installed command calls a small run() wrapper in cli.py. force=True replaces any existing root handlers, which is useful when an interactive environment has already configured logging.

One detail that surprises everyone: until logging.basicConfig runs, the root logger's default threshold is WARNING. Drop setup_logging() and your INFO lines vanish, not because they fail — because no handler and no permissive threshold exist yet. That is the severity gate working as designed: silence below the threshold is a feature.

5Wire logging into the pipeline

The command gains a logger, per-stage messages, and a guarded entry point.

Open this lesson's src/flight_delays/cli.py. It defines a module logger, validates raw input before cleaning, logs one INFO line per stage, and keeps command-line error handling in run():

src/flight_delays/cli.py (excerpt)
logger = logging.getLogger(__name__) def main( data_dir: Path | None = None, model_dir: Path | None = None, ) -> dict[str, float]: logger.info("Pipeline started") # --- Load + validate + clean ----------------------------------------- resolved_data_dir = data_dir or Path(os.environ.get("FLIGHT_DATA_DIR", DATA_DIR)) csv_path = resolved_data_dir / DATA_FILE ensure_file_exists(csv_path) logger.info("Loading data from %s", csv_path) raw_flights = load_csv(csv_path) ensure_columns(raw_flights, REQUIRED_RAW_COLUMNS) ensure_scheduled_departure_times(raw_flights) flights = clean_flights(raw_flights, target=TARGET) ensure_nonempty(flights, target=TARGET) X = flights[MODEL_INPUT_COLUMNS] logger.info("Modeling rows: %s", f"{len(flights):,}") # ... train + evaluate ... logger.info("Training finished") logger.info("accuracy: %.4f", metrics["accuracy"]) logger.info("f1: %.4f", metrics["f1"]) # ... save + predict ... logger.info("Saved pipeline to %s", model_path) logger.info("Pipeline finished") return metrics def run() -> None: setup_logging() try: main() except (FileNotFoundError, DataValidationError) as error: logger.error("Pipeline failed: %s", error) raise SystemExit(1) from error

Walk the pieces:

  • The validation chain. The file is checked before pandas opens it. Raw columns and HHMM values are checked before cleaning; the row count is checked after cleaning.
  • One message per stage. Loaded, trained, saved, done — each phase announces itself. Anyone skimming logs can now answer "where did it get to?" without reading code.
  • The command boundary. run() catches only FileNotFoundError and DataValidationError. Unexpected bugs keep their full traceback.

Exit codes are how one program reports to another: 0 means success, anything else means failure. raise SystemExit(1) stops the process with code 1; from error preserves the causal link for debugging. A scheduler or a CI job checks that code. Because only expected input failures are caught, an unexpected bug still crashes with its full traceback.

These console logs are not stored history; later lifecycle lessons record runs persistently.

Takeaways
  • A traceback is your WHERE-map: read the last line (exception type + message), then the frames for the call path. Keep it for unexpected bugs.
  • Expected breakage gets a designed message: validate at the boundary with raise, and catch only the exception families you can actually handle.
  • try/except/else/finally is the complete control flow: catch failures, act on the success path, always clean up.
  • logging replaces print(): five levels, per-module loggers via getLogger(__name__), printf-style formatting, and thresholds that can silence noise.
  • Configure once at the entry point. setup_logging() + one format string gives every future module the same timestamped, leveled voice.
Before the next lesson — what still hurts?

The pipeline now tells you when an expected input fails. But after the happy path runs, nothing checks that the metrics are still right — change one preprocessing line and the accuracy could silently drift. The generated model is also just a file: there is no recorded run connecting its data, code, parameters, and metrics.

  • Nothing proves the pipeline still works after you touch it → L1.5 checks the pipeline's behaviour automatically and repeatedly.
  • No record of which data + code version produced which model → L2.1 starts recording experiments and their inputs.
