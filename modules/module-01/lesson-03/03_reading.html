Clean, Typed, Consistent

Your pipeline runs, but the code has no style enforcement, no type declarations, and magic strings scattered across files. This lesson fixes all three — same pipeline, same numbers.

Before you start

You need Lesson 1.2 complete with the data pool at the repo root. If you have a src/ folder and uv run python main.py prints accuracy: 0.8952, you are ready.

Goal

Install Ruff and mypy, add type annotations to every function, consolidate duplicate pipeline logic, centralise config, and introduce a FlightDelayModel class — then prove the pipeline still produces the same metrics.

Time: ~45–60 minutes

What you will do

  • ☐ Install and run the Ruff formatter and linter on every .py file.
  • ☐ Add type annotations to every function and verify them with mypy.
  • ☐ Consolidate two pipeline-building functions into one DRY function.
  • ☐ Centralise all magic strings and defaults into a typed config.py.
  • ☐ Introduce a FlightDelayModel class that owns the prediction contract.
  • ☐ Confirm the pipeline still produces accuracy: 0.8952 and f1: 0.7415.

1. Why clean code matters

You have a working pipeline from Lesson 1.2. Run it, get the numbers, done. But open the code and you will notice three cracks that will only get worse as the project grows:

Crack 1: style drift. You format one way today, a teammate formats differently tomorrow. Every git diff mixes whitespace noise with real logic changes, and code review turns into a formatting argument.

Crack 2: invisible contracts. Look at train_model(model, X_train, y_train). What is model? What does the function return? You have to open the file and read the body to find out. Multiply that by every function, and nobody can reason about the code without reading everything.

Crack 3: magic strings. "ArrDel15", "model_2025_01.joblib", "flight_delays_2025_01.csv" appear directly in main.py. Rename the target and you must find and replace every occurrence. Forget one and you get a silent bug.

Each crack has a fix. The pattern is the same one you have seen before: problem → practice → tool → apply. Start with the easiest win: consistent formatting.

2. Ruff: formatting and linting

The problem

Your code runs, but it looks nothing like your teammate's code — or even your own code from last week. Indentation, spacing, line length, import order all differ. Every pull request mixes formatting noise with real changes.

The practice

Automate formatting so style is never a human decision. A formatter rewrites whitespace and punctuation to match a shared standard. A linter catches structural issues: unused imports, undefined names, common bugs.

The tool

Ruff is a single tool that does both. One command formats; another lints. It is fast, opinionated, and has become the Python community standard since 2024.

Add Ruff to your dev dependencies:

terminal
uv add --dev ruff

This writes "ruff>=0.9" into the [dependency-groups] dev section of pyproject.toml. Dev-only tools do not ship with your model; they are for local development only.

The formatter

Run the formatter on every .py file:

terminal
uv run ruff format src main.py

Ruff rewrites files in place. Here is what it does to a poorly formatted function:

Before ruff format

def evaluate_model(model,X_test,y_test):
  y_pred=model.predict(X_test)
  return {"accuracy":accuracy_score(y_test,y_pred),"f1":f1_score(y_test,y_pred)}

After ruff format

def evaluate_model(
    model,
    X_test,
    y_test,
):
    y_pred = model.predict(X_test)
    return {
        "accuracy": accuracy_score(y_test, y_pred),
        "f1": f1_score(y_test, y_pred),
    }

Same logic. Consistent style. No human debate needed.

The formatter config lives in pyproject.toml. The default 88-character line length is the PEP 8 community convention — just leave it:

pyproject.toml
[tool.ruff] target-version = "py311" [tool.ruff.lint] select = ["E", "F", "I"]

["E", "F", "I"] enables pycodestyle errors (E), pyflakes (F), and isort import ordering (I) — the three rule sets that catch real bugs and noise without overwhelming you.

The linter

The formatter fixes whitespace. The linter catches structural problems:

terminal
uv run ruff check src main.py

Common linter catches: F841 (variable assigned but never used), E402 (import at the top, not buried in code), F821 (undefined name). Fix what it reports. If a rule does not apply to your case, add a # noqa comment on that line with a short reason.

Check both

ruff format and ruff check are independent. You need both. Format first (so linter does not flag formatting), then lint.

Formatting is fixed. But open any function and you still have to read the body to know what it takes and returns. That is the next crack.

3. Type hints and mypy

The problem

Open train.py from Lesson 1.2:

src/train.py (L1.2)
def train_model(model, X_train, y_train): model.fit(X_train, y_train) return model

What is model? A list? A Pipeline? A custom object? What does the function return? You cannot tell from the signature. You have to open the file and read the body. Every caller must reverse-engineer the contract.

The practice

Type hints are annotations that declare the expected type of every argument and return value. They do not change runtime behaviour — Python ignores them. But they let two tools help you:

  • Your editor uses them for autocomplete and inline warnings.
  • mypy reads them and checks your code statically — before you run it.

The tool

mypy is the Python static type checker. It reads your hints and reports mismatches. Install it as a dev dependency:

terminal
uv add --dev mypy pandas-stubs

pandas-stubs provides type information for pandas — without it, mypy treats every DataFrame column as Any and misses real errors.

Annotating the functions

Open every .py file in src/ and add the annotation for every argument and return value. Here are the patterns you apply:

Before (untyped)

def train_model(model, X_train, y_train):
    model.fit(X_train, y_train)
    return model

After (typed)

def train_model(
    model: Pipeline,
    X_train: pd.DataFrame,
    y_train: pd.Series,
) -> Pipeline:
    """Fit the pipeline on training data."""
    model.fit(X_train, y_train)
    return model

Do the same for every function in load.py, clean.py, features.py, evaluate.py, and predict.py. The pattern is always:

annotation pattern
def function_name(arg: Type, ...) -> ReturnType:

The full list of new annotations in the project:

  • load_csv(path: Path | str) -> pd.DataFrame
  • clean_flights(df: pd.DataFrame) -> pd.DataFrame
  • build_model(...) -> Pipeline
  • train_model(...) -> Pipeline
  • save_model(model: Pipeline, model_path: Path) -> Path
  • evaluate_model(...) -> dict[str, float]
  • FlightDelayModel.predict_delay(self, features_df: pd.DataFrame) -> np.ndarray

config.py is all module-level constants — annotate them too:

src/config.py (excerpt)
REPO_ROOT: Path = Path(__file__).resolve().parents[5] DATA_DIR: Path = REPO_ROOT / "data" DATA_FILE: str = "flight_delays_2025_01.csv" FEATURES: list[str] = NUMERIC_FEATURES + CATEGORICAL_FEATURES TARGET: str = "ArrDel15" RANDOM_STATE: int = 42 MAX_ITER: int = 500

Running mypy

terminal
uv run mypy src main.py

mypy reads all files, follows imports, and checks every annotation against every call. A clean run prints Success: no issues found in 9 source files.

Common fixes when mypy complains:

  • Missing stubs — install uv add --dev pandas-stubs for pandas; add a [[tool.mypy.overrides]] block for sklearn (no official stubs).
  • Missing return type — every function needs -> ReturnType; None for functions that do not return.
  • Incompatible types — usually a real bug or a missing cast. Read the line number; mypy tells you what it found vs what it expected.
pyproject.toml (mypy config)
[tool.mypy] python_version = "3.12" disallow_untyped_defs = true [[tool.mypy.overrides]] module = ["sklearn.*", "joblib"] ignore_missing_imports = true

disallow_untyped_defs = true means mypy rejects any function without annotations — it forces you to complete the job.

mypy does not run your code

mypy is a static checker: it reads your .py files and your hints. It never imports or executes anything. That is why it is fast and safe — it cannot break your pipeline.

Formatting is consistent. Types are declared. Now look at structure: two functions that do one job, and magic strings in the orchestrator.

4. Single responsibility and DRY

With formatting and types in place, turn to structure. The Lesson 1.2 code has two structural problems: two functions that build one thing, and magic strings in the orchestrator.

DRY: two functions → one

In Lesson 1.2, build_preprocessor() and build_model() are separate functions. But the preprocessor is never used alone — every call to build_model() immediately wraps it in a Pipeline with the classifier. Two functions for one thing means two places to maintain when the preprocessing changes. This is a textbook violation of DRY — Don't Repeat Yourself.

Consolidate into a single build_model() that constructs the complete pipeline:

src/features.py
def build_model( numeric_features: list[str], categorical_features: list[str], max_iter: int = 500, random_state: int = 42, ) -> Pipeline: """Return the full pipeline: scaling, one-hot encoding, then logistic regression. Everything a feature row needs before classification — impute, scale, encode — lives inside this one pipeline. """ numeric = Pipeline( steps=[ ("imputer", SimpleImputer(strategy="median")), ("scaler", StandardScaler()), ] ) categorical = Pipeline( steps=[ ("imputer", SimpleImputer(strategy="most_frequent")), ("onehot", OneHotEncoder(handle_unknown="ignore")), ] ) preprocessor = ColumnTransformer( transformers=[ ("numeric", numeric, numeric_features), ("categorical", categorical, categorical_features), ] ) return Pipeline( steps=[ ("preprocessor", preprocessor), ( "classifier", LogisticRegression( max_iter=max_iter, class_weight="balanced", random_state=random_state, ), ), ] )

The caller in main.py shrinks from two calls to one:

Before (two calls)

preprocessor = build_preprocessor(...)
model = build_model(preprocessor)

After (one call)

model = build_model(
    NUMERIC_FEATURES,
    CATEGORICAL_FEATURES,
    max_iter=MAX_ITER,
    random_state=RANDOM_STATE,
)

build_preprocessor() is deleted from features.py and its import removed from main.py. One function, one place, one responsibility.

Magic strings → typed config

Lesson 1.2's main.py contains strings like "ArrDel15", "flight_delays_2025_01.csv", "model_2025_01.joblib", and the full feature list. These are decision-level choices embedded in the orchestrator. Change the target or the data file, and you must find and replace every occurrence.

Move every choice into src/config.py as a named, typed constant:

src/config.py
"""Project configuration — paths, features, and training defaults.""" from pathlib import Path # --- Paths ----------------------------------------------------------- REPO_ROOT: Path = Path(__file__).resolve().parents[5] DATA_DIR: Path = REPO_ROOT / "data" DATA_FILE: str = "flight_delays_2025_01.csv" MODEL_DIR: Path = Path(__file__).resolve().parent.parent / "models" MODEL_FILE: str = "model_2025_01.joblib" # --- Feature lists ----------------------------------------------------------- NUMERIC_FEATURES: list[str] = [ "DepDelay", "Distance", "CRSElapsedTime", "scheduled_departure_hour", "DayOfWeek", ] CATEGORICAL_FEATURES: list[str] = ["Reporting_Airline", "Origin", "Dest"] FEATURES: list[str] = NUMERIC_FEATURES + CATEGORICAL_FEATURES TARGET: str = "ArrDel15" # --- Training defaults ------------------------------------------------------- TEST_SIZE: float = 0.2 RANDOM_STATE: int = 42 MAX_ITER: int = 500

main.py imports the constants it needs. One place to change the target → every file sees the new value. And because every constant has a type, mypy catches mistakes like assigning a string to a Path variable.

Splitting train and save

In Lesson 1.2, train.py only contained train_model() and saving was done with an inline joblib.dump() call in main.py. This violates single responsibility: main.py should know what to save, not how.

Add a save_model() function to train.py and call it from main.py. The pattern applies in reverse for loading: a load() class method on the model object knows how to deserialize.

src/train.py
def train_model( model: Pipeline, X_train: pd.DataFrame, y_train: pd.Series, ) -> Pipeline: """Fit the pipeline on training data and return the fitted model.""" model.fit(X_train, y_train) return model def save_model(model: Pipeline, model_path: Path) -> Path: """Serialize the fitted pipeline to disk and return the path written.""" joblib.dump(model, model_path) return model_path

The project now has clean formatting, typed contracts, a DRY pipeline builder, a centralised config, and separate train/save responsibilities. One thing remains: the prediction path in predict.py still exposes two loose functions. When a fitted pipeline must be loaded once and reused for every prediction, that is state — and state earns a class.

5. OOP awareness: when state earns a class

You have been using objects all along — a pandas DataFrame is an object (it bundles rows with .head(), .groupby()), and a scikit-learn Pipeline is an object (it bundles steps with .fit(), .predict()). A class is just a way to bundle state with the functions that operate on it. This is not new vocabulary for something you already do.

When does a function need a class?

A class earns its keep when the thing you are modelling has state that must survive between calls. A function is enough when each call is independent.

The flight-delay prediction path has genuine state: a fitted Pipeline. Once trained, that artifact must be loaded once, held in memory, and reused for every incoming prediction. Two separate functions — load_model() and predict_delay() — work, but the caller must remember to load first and pass the artifact around. A class bundles the two and makes the state explicit.

The FlightDelayModel class

Open src/predict.py. The class has three parts:

src/predict.py
class FlightDelayModel: """A fitted flight-delay model with one job: predict delay probability.""" def __init__(self, pipeline: Pipeline) -> None: self._pipeline = pipeline @classmethod def load(cls, model_path: Path) -> "FlightDelayModel": """Load a fitted pipeline from disk and wrap it in a model object.""" return cls(joblib.load(model_path)) def predict_delay(self, features_df: pd.DataFrame) -> np.ndarray: """Return the probability that each row's flight is delayed.""" return self._pipeline.predict_proba(features_df)[:, 1]

Walk through each part:

  • __init__(self, pipeline) — the constructor. Takes a fitted Pipeline and stores it. The underscore prefix on self._pipeline signals: this is internal state; callers should not touch it directly.
  • load(cls, model_path) — a @classmethod: it belongs to the class, not to a particular instance. It deserializes the pipeline and returns a new FlightDelayModel wrapping it.
  • predict_delay(self, features_df) — the single public method. Takes a DataFrame of features, returns an array of delay probabilities. This is the contract: one input, one output, no side effects.

The caller in main.py is now two lines:

main.py (excerpt)
model = FlightDelayModel.load(model_path) delay_probability = model.predict_delay(X_test.iloc[:1])

No import joblib in main.py. No knowledge of how the pipeline was serialized. The class hides the mechanism; the caller works with the contract.

Why not just two functions?

Two functions work at this project size. But the class gives you one place to add input validation, logging, or a model registry later — not every call site. And when Module 4 builds an API endpoint, the endpoint receives a FlightDelayModel, not a loose function. That is why production MLOps code wraps models behind an object.

The over-OO anti-pattern

The opposite mistake is wrapping everything in classes for the sake of "object-oriented design": a CsvLoader class with a load() method that returns a DataFrame. A plain function load_csv(path) -> DataFrame is simpler and does the same job. Not every tool needs a class. Apply the rule: state earns a class; stateless behaviour stays a function.

Five changes. One lesson. Now prove nothing broke.

Try it

Open src/config.py and change TARGET: str = "ArrDel15" to TARGET: str = "DepDel15" (a column that does exist in the raw data, so it will not crash, but will produce different metrics). Run uv run python main.py and observe that the accuracy changes — the entire pipeline adapted to the new target by changing one constant. Now change it back.

Takeaways

  • A formatter (Ruff) makes style a tool decision, not a human decision. Run ruff format then ruff check; fix what it reports.
  • Type hints are documentation that mypy can verify. Every function gets an annotation; mypy catches mismatches before runtime.
  • DRY means one function owns one responsibility. If two functions always appear together, merge them.
  • Typed config replaces magic strings. One place to change the target, the data file, or the model path.
  • A class earns its keep when it bundles state that must survive between calls. Stateless behaviour stays a function.

Reflect

Before you move on, think about this: if you added a new feature — say, a weather column — how many files would you need to touch? With the typed config, the answer is one: config.py. Without it, you would hunt through main.py, features.py, and anywhere else the feature list was hardcoded. That is the payoff of centralised config.

Before the next lesson — what still hurts?

Open main.py and delete the CSV file path, or rename it to a file that does not exist. Run uv run python main.py. You get a raw Python traceback with no context about what went wrong. The pipeline prints accuracy: 0.8952 on success but gives you nothing except a crash on failure.

That is the symptom Lesson 1.4 fixes. It adds error handling (the pipeline catches bad inputs and reports them clearly) and logging (prints become structured log messages that tell you when, where, and why).

  • The CSV path is wrong → L1.4 adds a clean error message instead of a traceback.
  • print() is the only output mechanism → L1.4 introduces logging with severity levels.
  • There is no way to tell when the pipeline last ran successfully → L1.4 adds a timestamped log entry at each stage.
