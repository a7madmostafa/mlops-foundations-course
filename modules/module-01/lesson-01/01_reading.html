Your Starting Point: The Flight Delay Notebook

You get familiar with the data, build your own baseline model in a notebook, and see the problems that make notebooks dangerous in production — problems every later lesson will fix.

Notebook (HTML) CODE/
Before you start

You need Jupyter, pandas, scikit-learn, matplotlib, and joblib — nothing else. No new tools, modules, tests, logging, packaging, or refactoring.

First get the data. The course uses the US Flight Delays January 2025 file, one of 12 monthly files in the shared pool at the repo root in data/:

Download the dataset from Kaggle data/README.md — instructions

Or, from the repository root, run kaggle datasets download a7madmostafa/us-flight-delays-2025-bts-on-time-performance -p data --unzip.

What you'll do in this lesson

  • Understand the project — what you predict, when you predict it, and what the target means.
  • Build your own notebook: explore the data, clean it, engineer features, train a baseline model.
  • Run our reference notebook from a fresh kernel and record its baseline metrics.
  • Write a six-row Fragility Audit — a table of risks supported by evidence from the notebook.
  • Map each problem to the later lesson that will fix it.

1The project

What you are predicting, and where the data comes from.

The US Department of Transportation's Bureau of Transportation Statistics (BTS) publishes on-time performance for every domestic flight — carrier, origin, destination, scheduled and actual times, and delay breakdowns. The data is public, US-government open data.

After you download it, the course data pool at the repo root (data/, see data/README.md) holds the full 2025 corpus. This lesson uses flight_delays_2025_01.csv — January 2025, 539,747 flights, 40 columns.

The task is simple: shortly after departure, predict whether a flight will arrive 15 or more minutes late (the BTS definition of "delayed"). At that point the actual departure delay is known, while the arrival outcome is not. It is a binary classification problem. The target column is ArrDel15 — 1.0 means delayed, 0.0 means on time.

Here is what a few rows look like:

flight_delays_2025_01.csv (real rows)
Reporting_Airline Origin Dest CRSDepTime Distance ArrDel15 0 AA JFK LAX 659 2475 0.0 119 AA ORD MSY 1025 837 NaN 11 AA JFK LAX 700 2475 1.0

Features you can use at that prediction point include carrier, origin/destination airports, scheduled departure time, day of week, distance, actual departure delay, and scheduled elapsed time. The dataset is rich enough for real feature engineering — and small enough that a baseline model fits comfortably on a laptop (a random forest over half a million rows takes a few minutes at most).

2Build your own notebook

This is your hands-on work for this lesson.

Open a fresh Jupyter notebook and do what you always do:

  1. Load the data — read data/flight_delays_2025_01.csv into a DataFrame.
  2. Explore it — shape, dtypes, missing values, target distribution, distributions of key features.
  3. Clean it — drop rows that are not real flights (cancelled, diverted), handle missing values.
  4. Engineer features — whatever you think will help: hour of day, carrier encoding, distance bins, anything.
  5. Train a model — random forest, logistic regression, whatever you like. Split train/test, fit, predict.
  6. Check the metrics — accuracy, F1, classification report. Write down your numbers.

Take your time. There is no single right answer here. The point is to have your version before you see ours.

3Our notebook as a reference

One way to do it — not the only way.

Open CODE/flight_delays.ipynb (or read the HTML export). This is our version. It loads the data, cleans it, engineers a few features, trains a random forest, and prints the metrics. It is deliberately simple — the point is not a fancy model, but a working baseline.

When you run it cold (kernel restart → Run All), it prints:

cell 16 · output
accuracy: 0.9184 f1: 0.7587 precision recall f1-score support 0.0 0.93 0.97 0.95 84941 1.0 0.85 0.69 0.76 19513 accuracy 0.92 104454

Compare these numbers with yours. Different preprocessing, different features, different model — your numbers will be different, and that is fine. What matters is that you have a baseline: a number that every future change must not silently make worse.

4A notebook is a transcript, not a program

One concept first, because everything here hangs off it.

A notebook is a transcript of a session: a record of what you explored, in the order you explored it. That is exactly what makes it a fantastic exploration tool — and exactly what makes it a bad program.

A program

Fixed entry point, declared inputs and outputs, deterministic: same inputs → same outputs. You can run it without you.

  • Runs on a server
  • Fails loudly
  • Records its results

A notebook

Its "inputs" are whatever is in the kernel when a cell runs. The file does not run — you run it, and the result depends on choices no one wrote down.

  • Depends on session state
  • Silently passes in wrong order
  • Prints results and forgets them

A tiny example shows why "the notebook works" is not a verifiable claim. Three cells, each perfectly fine in isolation:

order_matters.py
# cell A price = 40 # cell B price = price + 10 # cell C price = price * 2

Run A → B → C and you get 100. Run A → C → B and you get 90. Same file, two answers, no error raised. Run B or C first in a fresh kernel and you get a NameError, because price does not exist yet. Now imagine price is your preprocessed test set, and you will see why "it runs" tells you almost nothing you can trust.

5Read the notebook like an engineer

Cell by cell: what is pipeline, and what is exploration?

You have read notebooks a hundred times as a data scientist — visual by visual, insight by insight. Today, read ours once more, differently. Classify every cell into one of two buckets:

  • Pipeline cells — the ones that should be a program: load, clean, features, encode, split, train, evaluate, save.
  • Exploration cells — the ones that belong to a session: plots, notes, "let me see the distribution", throwaway tries.

6What is wrong with this notebook

Six problems, each with a code snapshot from the actual cell. Every problem maps to a future lesson.

1 · The machine is baked in

The data path and model path are hardcoded relative to wherever you launched Jupyter. On anyone else's machine, these point nowhere.

cells 4 + 17
df = pd.read_csv("../../../../data/flight_delays_2025_01.csv") joblib.dump(model, "models/model_2025_01.joblib")

Why it matters: the exact file these numbers came from lives only in your head. Two weeks later, even you will not know.

FIXED IN: L1.2 · paths become configuration

2 · The environment is unrecorded

Which versions of pandas and scikit-learn produced these numbers? Nowhere, is where. On another machine the same code can silently behave differently.

cell 3 · imports
import pandas as pd import numpy as np from sklearn.ensemble import RandomForestClassifier

Why it matters: no requirements.txt, no pyproject.toml, no lockfile — nothing records the runtime that made the model.

FIXED IN: L1.2 · dependency management, uv + lockfile

3 · The pipeline is invisible

"Preprocessing" is spread across cells 8–13 — cleaning, feature engineering, encoding, scaling — in no enforced order. You cannot import it, run it alone, or prove the model used the steps you are staring at.

cells 8–13 (fragment)
# cell 8: clean df = df[df["Cancelled"] == 0] # cell 12: one-hot encoding cat = pd.get_dummies(df[["Reporting_Airline", "Origin", "Dest"]]) # cell 13: scaling sc_num = sc.fit_transform(num)

Why it matters: the recipe for the model is only as trustworthy as a wall of manually-walked-in-order cells.

FIXED IN: L1.2 · importable modules · and L1.3 · single responsibility

4 · Code is repeated and unverified

Cells 8 and 9 both drop cancelled and diverted flights — the same filter, twice, already drifting in wording. And nothing checks that any intermediate output is correct.

cells 8 + 9
# cell 8 df = df[df["Cancelled"] == 0] df = df[df["Diverted"] == 0] # cell 9 df = df[df["Cancelled"] == 0] df = df[df["Diverted"] == 0]

Why it matters: the copy drifts (first it says "cancelled/diverted", then "no survivor"), and nobody notices — or proves — anything.

FIXED IN: L1.3 · DRY · and L1.5 · tests

5 · Results are printed, not produced

The most important number in the project exists as text in a cell you ran once. There is no record of how this model was made — data, features, parameters.

cell 16
print("accuracy:", accuracy_score(y_test, y_pred)) print("f1:", f1_score(y_test, y_pred))

Why it matters: a metric that only exists as a printed float cannot be compared, tracked, or verified later.

FIXED IN: L1.4 · logging · and later L2.x · experiment tracking

6 · Data leakage inflates the metrics

Cells 12–13 one-hot encode and scale before the train/test split in cell 15. The scaler and encoder have already seen the test rows, so the test metrics are quietly optimistic.

cells 12–13 then cell 15
# cell 12: encode (before split!) cat = pd.get_dummies(df[["Reporting_Airline", "Origin", "Dest"]]) # cell 13: scale (before split!) sc_num = sc.fit_transform(num) # cell 15: split happens after encoding X_train, X_test, y_train, y_test = train_test_split(X, y, ...)

Why it matters: no crash, just a lying score. The reported 0.7587 F1 is higher than what you would see on genuinely unseen data.

FIXED IN: L1.5 · tests that catch it
Notebooks are not the enemy

Jupyter is the right tool for exploration — this disease hunt lives in one, after all. The problem is using it (only) as the vehicle for code that must run reliably later. Every line above is about the use, not the tool.

Takeaways

You know the data: 539,747 US flights from January 2025, 40 columns, binary target ArrDel15.
You built your own baseline and saw our reference — accuracy ≈ 0.918, F1 ≈ 0.759.
A notebook is a transcript of a session, not a program: its result depends on what has already run, and the file never records that.
Our notebook has six concrete problems, each mapped to the lesson that fixes it. That mapping is the course roadmap.
