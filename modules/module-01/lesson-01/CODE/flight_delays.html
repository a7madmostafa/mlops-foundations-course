Flight Delays — Starting Notebook¶

You will build a baseline model that predicts whether a US domestic flight will arrive 15 or more minutes late (ArrDel15). The prediction is made shortly after departure, so actual departure delay is known but the arrival outcome is not.

8. Choose the features (8 of 40 columns)¶

The prediction is made shortly after departure. Most of the 40 columns cannot be features: some are the answer itself, some are only known at arrival, some duplicate each other, and some are identifiers. The 8 that survive are exactly what a model can legitimately see at prediction time.

Feature Why it is a feature
DepDelay (numeric) the strongest predictor (section 7)
Distance (numeric) known before departure
CRSElapsedTime (numeric) scheduled duration, known in advance
scheduled_departure_hour engineered from CRSDepTime (section 3)
DayOfWeek (numeric) calendar context
Reporting_Airline (cat) who operates the flight
Origin (cat) where the flight departs
Dest (cat) where the flight arrives

Why the other 32 stay out:

  • The target — ArrDel15 is what we predict, so it cannot be a feature.
  • Only known after arrival (leakage) — ArrTime, ArrDelay, ArrDelayMinutes, ActualElapsedTime, AirTime, TaxiIn, WheelsOn. Not available at prediction time.
  • Delay-cause columns — CarrierDelay, WeatherDelay, NASDelay, SecurityDelay, LateAircraftDelay. Filled in only after the flight and ~82% missing (section 2).
  • Duplicates — DepDelayMinutes restates DepDelay; DepDel15 is the same delay as a 0/1 flag; DepTime is CRSDepTime + DepDelay; OriginCityName/OriginState repeat Origin; DestCityName/DestState repeat Dest.
  • Identifiers / constants — FlightDate and Flight_Number_Reporting_Airline identify one row each; Year, Quarter, Month are constant in this file; DayofMonth was not selected.
  • Row filters — Cancelled, CancellationCode, Diverted already decided which rows stay (section 3).
  • Summarized elsewhere — CRSDepTime is replaced by scheduled_departure_hour; CRSArrTime and CRSElapsedTime say the same thing about the timetable; TaxiOut/WheelsOff are measured during departure and add little beyond DepDelay.

Keep numeric and categorical columns separate. Split the raw rows now; the preprocessing pipeline will learn medians, scales, and categories from the training set only.

9. Build one preprocessing and model pipeline¶

Numeric columns receive median imputation and StandardScaler. Categorical columns receive most-frequent imputation and OneHotEncoder. handle_unknown="ignore" lets the fitted model accept a carrier or airport category that was absent from the training split.

Logistic regression is a clear baseline for this transformed feature space. Unlike a random forest, it benefits from scaled numeric inputs.

In [21]:
numeric_pipeline = Pipeline(
    steps=[
        ("imputer", SimpleImputer(strategy="median")),
        ("scaler", StandardScaler()),
    ]
)

categorical_pipeline = Pipeline(
    steps=[
        ("imputer", SimpleImputer(strategy="most_frequent")),
        ("onehot", OneHotEncoder(handle_unknown="ignore")),
    ]
)

preprocessor = ColumnTransformer(
    transformers=[
        ("numeric", numeric_pipeline, numeric_features),
        ("categorical", categorical_pipeline, categorical_features),
    ]
)

model = Pipeline(
    steps=[
        ("preprocessor", preprocessor),
        (
            "classifier",
            LogisticRegression(
                max_iter=500,
                class_weight="balanced",
                random_state=42,
            ),
        ),
    ]
)

Notes to self¶

The ML workflow is sound enough for a baseline, but it is not yet an operable ML system:

  • data and artifact paths are hardcoded
  • library versions are not recorded
  • loading, cleaning, training, evaluation, and saving are trapped in notebook cells
  • schema and preprocessing assumptions are not tested
  • metrics are printed but no run history records their provenance.

These are five risks . The next lessons move this workflow into importable, testable, diagnosable project code.
