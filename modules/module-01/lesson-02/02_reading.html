Notebook → Project

You turn the flight-delay notebook into an installed Python package, manage its dependencies with uv, and reproduce the baseline through one reliable command.

CODE/
Before you start

You need the data pool present (see data/README.md) and the Lesson 1.1 notebook metrics recorded. No new ML concepts today — same data, same pipeline, same numbers. You will learn a new tool (uv) as you go — no prior experience needed.

What you'll do in this lesson

  • Install uv and use it to create a virtual environment with recorded dependencies.
  • Split the notebook into importable modules under src/flight_delays/.
  • Move hardcoded paths into a central config.py with sensible defaults.
  • Install the package and expose a flight-delays command that reproduces the baseline.

1Why a notebook is not enough

The fragility audit from L1.1 pointed here first.

In Lesson 1.1 you recorded five risks the notebook carries. Two of them are about structure: the workflow is trapped across cells that cannot be imported or run as one command, and the machine is baked in through hardcoded relative paths. This lesson fixes both.

Consider what happens when a teammate asks: "Can I reproduce your model?" Today you would hand them the notebook, tell them to launch Jupyter from the right folder, and hope they have the same library versions. That is not reproducibility — it is a favour request.

Before

  • One .ipynb file
  • Hardcoded path ../../../../data/...
  • No dependency record
  • Requires Jupyter to run

After

  • An installed flight_delays package
  • Paths live in config.py
  • pyproject.toml + uv.lock
  • uv run flight-delays

2Meet uv

The tool that records your dependencies and makes your project reproducible.

The problem

Your notebook uses pandas, scikit-learn, numpy, and others. But which versions? The notebook does not say. If a teammate installs different versions, the same code can produce different numbers — or fail outright. You need two things:

  1. A list of what your project needs — so anyone can install the same packages.
  2. An isolated environment — so this project's packages do not clash with other projects on the same machine.

What is a virtual environment?

A virtual environment is a self-contained folder with its own Python interpreter and installed packages. Your system Python stays untouched. When you "activate" the environment, commands like python and pip point to the isolated copy instead of the system one.

Why does this matter? Without it, Project A might need pandas 2.1 while Project B needs 2.2. On the system Python, only one version can exist. With virtual environments, each project has its own.

What is uv?

uv is a fast Python package manager that handles everything in one tool:

  • Create a virtual environment
  • Install packages into it
  • Lock exact versions in a reproducible file
  • Run commands inside the environment

It replaces the older pip + venv + pip-tools workflow with a single, fast tool. You will use uv for the rest of this course.

Install uv

terminal
pip install uv

Or see the official installation guide for other methods (standalone installer, Homebrew, etc.). Verify it worked:

terminal
uv --version

Initialize the project

uv init scaffolds a brand-new project in an empty folder. Our CODE/ folder already ships a finished project, so you cannot run it there — uv will refuse with Project is already initialized. Instead, create a scratch folder outside the course, and run it there to see exactly what a fresh project contains:

terminal
mkdir scratch-uv && cd scratch-uv uv init

This creates:

  • pyproject.toml — the project description file, pre-filled with placeholder values (more on this below).
  • .python-version — tells uv which Python version this project uses.
  • README.md — a starter readme.
  • .gitignore and a .git/ folder — it even runs git init for you and adds a reasonable ignore list.
  • src/scratch_uv/__init__.py — a starter package (note the name: the folder name with hyphens swapped for underscores) containing a demo main() that prints Hello from scratch-uv!.

Open the generated pyproject.toml and you will see several things we need to deal with:

scratch-uv/pyproject.toml
[project] name = "scratch-uv" # defaults to the FOLDER name version = "0.1.0" description = "Add your description here" # placeholder text requires-python = ">=3.12" dependencies = [] # empty until you run uv add [project.scripts] # demo console command scratch-uv = "scratch_uv:main" [build-system] # for building/publishing a package requires = ["uv_build>=0.12,<0.13"] build-backend = "uv_build"

Four things to understand here:

  1. name comes from the folder name. Since you created scratch-uv, that is what uv used. In our real project we rename it to flight-delays.
  2. description is a placeholder. It waits for you to write a real one.
  3. [project.scripts] creates a command. The generated command calls a Python function. In our project, we rename it to flight-delays and point it at flight_delays.cli:main.
  4. [build-system] makes installation possible. It tells uv how to install the code under src/. This matters even when you are not publishing: your environment imports the installed package, not a folder that happens to be nearby.

After editing the name, description, command, and package target, our file is nearly ready. You will see the finished CODE/pyproject.toml in the next subsection, once the dependencies are filled in.

These commands run in scratch-uv, not in CODE/

The CODE/ folder ships the finished result, so uv init inside it fails by design, and uv add there would re-write the shipped dependency minimums. Use scratch-uv as your playground pad to watch every command work on a live project — that is the best way to learn a tool. When you are ready to run the real project, head to CODE/ and just run uv sync — its pyproject.toml and uv.lock are already in place. Delete the scratch-uv folder when you are done.

Add the dependencies

Our pipeline needs four packages. Add them all in one command:

terminal
uv add pandas scikit-learn numpy joblib

uv add does everything for you — no separate sync needed afterwards. In one command it:

  1. Adds each package to pyproject.toml under dependencies.
  2. Installs the packages into .venv/ right away (creating the environment on its first run).
  3. Updates uv.lock with the exact resolved versions.

Note that uv add wrote the newest versions it found (e.g. pandas>=3.0.5). The file shipped in CODE/ states lower minimums (e.g. pandas>=2.2) — that is fine, and irrelevant to how it runs, because the lockfile decides the exact installed version. Here is the shipped pyproject.toml:

pyproject.toml
[project] name = "flight-delays" version = "0.1.0" description = "US flight-delay prediction pipeline" requires-python = ">=3.12" dependencies = [ "pandas>=2.2", "scikit-learn>=1.5", "numpy>=1.26", "joblib>=1.4", ] [project.scripts] flight-delays = "flight_delays.cli:main" [build-system] requires = ["uv_build>=0.12.9,<0.13.0"] build-backend = "uv_build"

Each line under dependencies names a package and a minimum version. The >= means "this version or newer." You do not need to list every sub-dependency — uv resolves those automatically. The final two sections install src/flight_delays/ and turn its cli.main() function into the command learners run.

Or uv sync: the reverse direction

With uv add, everything is already installed and locked, so why would you ever run uv sync? uv sync goes the other way: instead of recording what you need, it makes your environment match what is already recorded. You run it whenever you get a project that already has a pyproject.toml and uv.lock — after cloning a repo, or here, in the already-shipped CODE/ folder:

terminal
uv sync --locked

It installs the locked resolution appropriate for your operating system and Python version, and creates .venv/ if needed. The --locked flag refuses to change an out-of-date lockfile. Platform-specific wheels can differ even when package versions match.

Which command do I use?

You are adding a new package or changing a version → uv add (installs and locks in one step).
You just received a project with its files already in place → uv sync --locked (recreate its recorded environment without rewriting the lockfile).

What files did uv create?

FileWhat it isWho creates itCommitted to git?

You never commit the virtual environment or its packages. You commit pyproject.toml and uv.lock. A teammate runs uv sync --locked to rebuild the environment with the recorded versions for their supported platform.

Common uv commands

You will only need a handful of commands. Here they are with what they do:

CommandWhat it does
uv initScaffold a project in an empty folder: pyproject.toml, .python-version, README.md, .gitignore, a starter src/<name>/__init__.py, and a .git/ repo. Fails if a pyproject.toml already exists.
uv add pandasAdd a package to pyproject.toml, install it, and update the lockfile — all in one step. Add several at once: uv add pandas scikit-learn.
uv remove pandasRemove a package from pyproject.toml, uninstall it, and update the lockfile.
uv syncReverse direction: recreate the environment to match the recorded pyproject.toml + uv.lock. Run this after cloning a repo or on a shipped project.
uv run flight-delaysRun the command installed from [project.scripts] inside the project environment.
uv run pythonOpen an interactive Python shell inside the environment.

You do not need to "activate" the environment manually. uv run handles that for you — it runs the command inside the environment automatically.

3Scripts, modules, and packages

Three terms you will see everywhere — defined once, used for the rest of the course.

Now that you have an environment, let us define how Python code is organized.

A script is a .py file you run directly. A module is a .py file you import, such as from flight_delays.load import load_csv. A package groups related modules under one import name. Here that name is flight_delays.

The outer src/ folder is a source layout, not the package name. Keeping importable code one level below the repository root prevents Python from importing an uninstalled checkout by accident. If uv sync has not installed the package correctly, the import fails immediately instead of giving you a misleading success.

project layout
CODE/ pyproject.toml # project metadata + dependencies (from uv init + uv add) uv.lock # locked package versions (from uv add / uv sync) .python-version # Python version for this project (from uv init) src/ # source-layout boundary flight_delays/ # installed package — you import this __init__.py # initializes the package __main__.py # supports python -m flight_delays cli.py # command entry point config.py load.py clean.py features.py train.py evaluate.py predict.py .venv/ # virtual environment (gitignored)

The rule is simple: cli.py orchestrates the workflow, while the other modules do focused jobs. The build system installs flight_delays, and the console entry point gives users a stable command even if files are reorganized later. The same installed package can be imported by later tests and services.

4The config module

One place for all paths and constants.

Hardcoded paths are the first thing that breaks when you change machines or folders. A config.py module collects every path and constant in one file. Change it there, and the whole project follows.

We use pathlib.Path instead of raw strings. Path objects know your operating system's separator (/ on Mac/Linux, \ on Windows), so paths work on any machine without extra code.

src/flight_delays/config.py
"""Project configuration — paths, feature lists, and constants.""" from pathlib import Path # --- Paths ------------------------------------------------------------------- # Data lives in the shared course data pool at the repository root. # The default works when you run from the lesson's CODE/ folder. REPO_ROOT = Path(__file__).resolve().parents[6] DATA_DIR = REPO_ROOT / "data" MODEL_DIR = Path(__file__).resolve().parents[2] / "models" # --- Feature lists ----------------------------------------------------------- NUMERIC_FEATURES = [ "DepDelay", "Distance", "CRSElapsedTime", "scheduled_departure_hour", "DayOfWeek", ] CATEGORICAL_FEATURES = ["Reporting_Airline", "Origin", "Dest"] # --- Training defaults ------------------------------------------------------- TEST_SIZE = 0.2 RANDOM_STATE = 42 MAX_ITER = 500

Path(__file__).resolve().parents[6] reaches the repository root from the installed package file (flight_delays → src → CODE → lesson-02 → module-01 → modules → repo root). From there, REPO_ROOT / "data" points to the shared data pool. parents[2] reaches this lesson's CODE/ folder for generated models.

The feature lists and training defaults live here too. Later lessons will add to this file; for now it gives you one place to change the random seed or the test size.

5Extract the pipeline functions

One function per file, one responsibility per function.

The notebook has the entire pipeline in a linear sequence of cells. We split it into functions that each do one thing. Each function goes in its own file so it can be imported independently.

5.1 Load

The notebook's cell 2 reads a CSV. We wrap it in a function so the path can be passed in instead of hardcoded:

src/flight_delays/load.py
"""Load the flight-delays CSV into a DataFrame.""" import pandas as pd def load_csv(path): """Read a flight-delays CSV and return a DataFrame.""" return pd.read_csv(path)

5.2 Clean

Cells 7 – 13 filter out cancelled and diverted flights, remove duplicates, and derive scheduled_departure_hour. This is the cleaning step — it takes raw data in and returns a clean cohort:

src/flight_delays/clean.py
"""Clean raw flight data into a modeling cohort.""" import pandas as pd def clean_flights(df, target): """Drop cancelled/diverted flights, duplicates, and add features.""" flights = ( df.loc[ df["Cancelled"].eq(0) & df["Diverted"].eq(0) & df[target].notna() ] .drop_duplicates() .copy() ) flights["scheduled_departure_hour"] = ( flights["CRSDepTime"].floordiv(100).astype(int) ) return flights

5.3 Features

Cells 20 – 21 build the scikit-learn preprocessing pipeline and the classifier. We extract two functions — one for the preprocessor, one for the full model:

src/flight_delays/features.py
"""Feature lists and pipeline construction.""" from sklearn.compose import ColumnTransformer from sklearn.impute import SimpleImputer from sklearn.linear_model import LogisticRegression from sklearn.pipeline import Pipeline from sklearn.preprocessing import OneHotEncoder, StandardScaler def build_preprocessor(numeric_features, categorical_features): """Return a ColumnTransformer that scales numerics and one-hot encodes categoricals.""" numeric_pipeline = Pipeline( steps=[ ("imputer", SimpleImputer(strategy="median")), ("scaler", StandardScaler()), ] ) categorical_pipeline = Pipeline( steps=[ ("imputer", SimpleImputer(strategy="most_frequent")), ("onehot", OneHotEncoder(handle_unknown="ignore")), ] ) return ColumnTransformer( transformers=[ ("numeric", numeric_pipeline, numeric_features), ("categorical", categorical_pipeline, categorical_features), ] ) def build_model(preprocessor, max_iter=500, random_state=42): """Return a Pipeline that preprocesses then classifies.""" return Pipeline( steps=[ ("preprocessor", preprocessor), ( "classifier", LogisticRegression( max_iter=max_iter, class_weight="balanced", random_state=random_state, ), ), ] )

5.4 Train and evaluate

Cells 22 – 23 fit the model and compute metrics. We keep these as thin wrappers so they are easy to swap out later (e.g., when you try a different classifier in L1.3):

src/flight_delays/train.py
"""Train the flight-delay model.""" def train_model(model, X_train, y_train): """Fit the pipeline on training data and return the fitted model.""" model.fit(X_train, y_train) return model
src/flight_delays/evaluate.py
"""Evaluate a fitted model on test data.""" from sklearn.metrics import accuracy_score, f1_score def evaluate_model(model, X_test, y_test): """Return a dict with accuracy and F1 on the test set.""" y_pred = model.predict(X_test) return { "accuracy": accuracy_score(y_test, y_pred), "f1": f1_score(y_test, y_pred), }

5.5 Predict

The pipeline saves the fitted model at the end. predict.py is the other half of that deal — it loads the artifact back and turns flight rows into delay probabilities. This mirrors what a serving system will do after training, on data the pipeline has never seen:

src/flight_delays/predict.py
"""Load a saved model and predict delay probabilities.""" import joblib def load_model(model_path): """Load a saved fitted pipeline from disk and return it.""" return joblib.load(model_path) def predict_delay(model, features_df): """Return the estimated delay probability (ArrDel15) for each row.""" return model.predict_proba(features_df)[:, 1]

predict_proba(...)[:, 1] reads the column of a binary classifier's two probability columns that belongs to class 1 — our delayed class. The function returns one probability per row.

6The entry point

One installed command that wires everything together.

src/flight_delays/cli.py contains main(), the function named by [project.scripts]. It runs the full pipeline: load → clean → split → train → evaluate → save → predict. A teammate runs it through the installed command:

src/flight_delays/cli.py (excerpt)
"""Flight-delay pipeline — entry point.""" import os from pathlib import Path import joblib from sklearn.model_selection import train_test_split from flight_delays.clean import clean_flights from flight_delays.config import ( CATEGORICAL_FEATURES, DATA_DIR, MAX_ITER, MODEL_DIR, NUMERIC_FEATURES, RANDOM_STATE, TEST_SIZE, ) from flight_delays.evaluate import evaluate_model from flight_delays.features import build_model, build_preprocessor from flight_delays.load import load_csv from flight_delays.predict import load_model, predict_delay from flight_delays.train import train_model def main(): csv_path = Path(os.environ.get("FLIGHT_DATA_DIR", DATA_DIR)) / "flight_delays_2025_01.csv" print(f"Loading {csv_path} ...") df = load_csv(csv_path) flights = clean_flights(df, target="ArrDel15") print(f"Modeling rows: {len(flights):,}") X = flights[NUMERIC_FEATURES + CATEGORICAL_FEATURES] y = flights["ArrDel15"].astype(int) X_train, X_test, y_train, y_test = train_test_split( X, y, test_size=TEST_SIZE, random_state=RANDOM_STATE, stratify=y, ) preprocessor = build_preprocessor(NUMERIC_FEATURES, CATEGORICAL_FEATURES) model = build_model(preprocessor, max_iter=MAX_ITER, random_state=RANDOM_STATE) train_model(model, X_train, y_train) metrics = evaluate_model(model, X_test, y_test) print(f"accuracy: {metrics['accuracy']:.4f}") print(f"f1: {metrics['f1']:.4f}") MODEL_DIR.mkdir(parents=True, exist_ok=True) model_path = MODEL_DIR / "model_2025_01.joblib" joblib.dump(model, model_path) print(f"\nSaved pipeline to {model_path}") loaded_model = load_model(model_path) delay_probability = predict_delay(loaded_model, X_test.iloc[:1]) print(f"\nPredicted delay probability for the first test flight: {delay_probability[0]:.4f}") print("\nDone.") if __name__ == "__main__": main()

Four things in this file are worth stopping on.

Environment variables. An environment variable is a named value stored outside your code, usually in your terminal session or operating system. The line os.environ.get("FLIGHT_DATA_DIR", DATA_DIR) says: "look for a variable named FLIGHT_DATA_DIR; if it does not exist, use the default from config.py." This lets you override the data path per machine without changing code. This is the "code vs configuration" pattern — the code is fixed, the configuration changes per machine.

Saving the model. joblib is a library that serializes Python objects — it writes a fitted scikit-learn pipeline to a file so you can load it later without retraining. The pipeline now runs: load → clean → split → train → evaluate → save → predict. The saved models/model_2025_01.joblib file is loaded back in the very next step.

Predicting right after training. The script does not stop after saving. It loads the artifact back with load_model and predicts a delay probability for the first test flight. This round-trip proves the file you keep is the model you will actually serve later. The preprocessing never re-runs here — the fitted pipeline already contains it, so one feature row (X_test.iloc[:1]) goes straight to predict_proba. This is the shape of serving we will build in Module 4.

Two ways into the same function. uv run flight-delays calls cli.main() through the console entry point. The small __main__.py file calls that same function, so uv run python -m flight_delays is an equivalent Python-native form. There is one workflow, not two copies.

7Run it — the milestone

This is your verification step: one command reproduces the notebook numbers.

terminal
uv run flight-delays

Run it from the CODE/ folder and you should see:

output
Loading /path/to/data/flight_delays_2025_01.csv ... Modeling rows: 522,269 accuracy: 0.8952 f1: 0.7415 Saved pipeline to models/model_2025_01.joblib Predicted delay probability for the first test flight: 0.0550 Done.

The same accuracy and F1 as the notebook — same data, same pipeline, same random seed. But now the result is produced by a program, not a session transcript.

If your data lives somewhere else, override the path with an environment variable. On Mac/Linux:

terminal
FLIGHT_DATA_DIR=/other/path uv run flight-delays

On Windows PowerShell:

terminal
$env:FLIGHT_DATA_DIR="C:\other\path"; uv run flight-delays
Common mistakes
  • Running from the wrong folder. uv sync and uv run must run from the CODE/ folder — that is where pyproject.toml lives. Elsewhere, uv will not find your project.
  • Skipping uv run. Typing only flight-delays may use the wrong environment or fail to find the installed command. uv run selects this project's environment.
  • Committing .venv/. The code in this lesson ignores it via .gitignore. Never add it to git.
  • Editing pyproject.toml by hand to change dependencies. Let uv add / uv remove do it for you — they update the file, the environment, and the lockfile together. If you do edit it by hand, re-run uv sync so the environment and lockfile catch up.

Takeaways
  • uv init creates the project skeleton; uv add records, installs, and locks a dependency in one step; uv sync rebuilds the environment from the recorded files.
  • pyproject.toml declares what your project needs; uv.lock records what was actually installed.
  • A script is a .py file you run; a module is one you import; a package is a folder with __init__.py.
  • config.py centralises paths and constants so the rest of the code never hardcodes them.
  • One installed entry point (uv run flight-delays) replaces the notebook-as-program: same numbers, importable code, configurable paths.
Before the next lesson — what still hurts?

Your project runs, but if a teammate handed it to you, you would notice three cracks:

  • main() coordinates many steps and still contains decision-level strings and defaults. A reader must scan the orchestrator to discover the project contract.
  • Nothing checks the code's style or catches simple mistakes before run time — two people will hand back two differently formatted src/ folders, and a typo in a column name only explodes when a cell calls it.
  • The fitted pipeline owns imputation, scaling, and encoding, but scheduled_departure_hour is still derived before the model. A new prediction caller could forget or change that rule.

L1.3 addresses all three: names and responsibilities become clearer, automated checks enforce code contracts, and scheduled-time derivation moves into the saved pipeline used by both training and prediction.
